## 0. О документе

### 0.1. Условные обозначения
- Обычный текст — нормативный.
- **`[E]`** — экспериментально: идеологически нужно, но в первой реализации необязательно.
- Примеры записаны в стандартной текстовой проекции (§4). Проекция — не сам язык: язык — это семантическое представление (§3).

### 0.2. Принятые решения
| # | Решение | Принцип |
|---|---|---|
| D1 | **Только VM.** Программы исполняются VM над семантическим представлением: интерпретатор — основа, JIT — специализация по живым типам. AOT-бинарей нет. | Единый источник семантики: исполняется и анализируется одно представление. |
| D2 | **Простое ядро + мутируемый интерпретатор.** Минимальный базовый язык; VM расширяется кодом на лету. | Минимальное ядро проще проверять; расширяемость живёт в коде языка. |
| D3 | **Текстовая проекция C-подобная, функции без ключевого слова:** `f(a, b) => …`, `x = 1` (объявление с выводом, §4.3), `T x = 1`, тип слева, `if(…)` со скобками. | Привычный синтаксис снижает порог входа; проекция не влияет на семантику. |
| D4 | **Типы — теги** (номинальная идентичность). Полиморфизм утиный, на месте использования, через инстанцирование. Анонимные агрегаты структурные, есть opaque. `A\|B` — не основа. | Номинальная идентичность даёт предсказуемые границы типов и специализацию. |
| D5 | **Мутация compile-time состояния — глобальная.** Любая сущность — идентификатор плюс композиция всех её расширений из любого места программы. Порядок — порядок инстанцирования (D14). | Расширения сущности композиционны и не зависят от места в тексте. |
| D6 | **Исключения, контексты и конкурентность — строго.** Статические исключения встроены; контексты — лексические блоки, переопределяющие операции; конкурентность — стековые файберы (гринтреды) с блокирующим API, push-модель. Системы эффектов нет. | Исключения и контексты статически видимы и ничего не стоят в рантайме; конкурентность без раскраски функций. |
| D7 | **Источник истины — база AST (семантическое представление).** Текст — проекция для чтения и ввода. | Источник истины — структура, а не текст: правки точечны и обратимы. |
| D8 | **Бэкенд полностью свой:** JIT-кодогенераторы по операциям прямо в машинный код. Ни LLVM, ни C. | Один путь исполнения без внешних бэкендов: полный контроль над кодогенерацией. |
| D9 | **Реализация VM и базового языка — C++26.** Самохостинг — после (§16). | Базовый слой пишется на языке с нужным контролем над памятью. |
| D10 | **Семантический инлайн по умолчанию.** Всё, что можно заинлайнить, инлайнится и получает семантику инлайна. Запрет — `outline`. | Инлайн как семантика, а не оптимизация: поведение не зависит от решений компилятора. |
| D11 | **Одна семантика compile-time и runtime,** стадия выводится, `constexpr` нет. | Одна семантика на всех стадиях: меньше особых случаев. |
| D12 | **Нет UB,** поведение определяется позитивно. | Поведение определяется позитивно («что точно существует»), а не списком запретов. |
| D13 | **Безопасность: различать, а не запрещать.** Мутации через алиасы разрешены. Анализ отличает «опасное-безопасное» от «опасного-опасного»: доказанно опасное — ошибка, недоказанное — проверка VM или предупреждение по уровню статичности. | Безопасность через различение опасного и безопасного, а не общий запрет. |
| D14 | **Порядок compile-time мутации — порядок инстанцирования.** Состояние — это состояние инстанцирования с побочными эффектами; связывание контекста — в момент вызова. Реактивная VM отслеживает эффекты и переинстанцирует зависимых. | Детерминизм: результат зависит от явного, наблюдаемого порядка инстанцирования. |
| D15 | **Слои и пути — часть ядра среды.** Срезы («только то, что использует x»), программа для заданных входов, многослойные функции (статическая основа + динамические слои), расширение конкретной функции ссылкой, отладка с инлайн-семантикой. | Срезы и слои — часть ядра: инструменты видят программу так же, как исполнитель. |
| D16 | **VM как ОС:** классы процессов (монопольный на P-ядрах, фоновый на E-ядрах, мультиплексирование), кооперативное переключение с редким вытеснением, пакетный ввод-вывод, системный рантайм (криптография, сеть, IPC) — сервисы внутри VM. | Ресурсы выдаются явно; изоляция процессов в одной VM без копирования данных. |

### 0.3. Что изменилось
**v0.2 → v0.3**:
- Правило эксклюзивности алиасов (облегчённый borrow checker) убрано — это ровно то, за что автор критикует Rust. Взамен — анализ опасных мутаций (D13, §12.1).
- Фазы D/B для compile-time мутации (моё изобретение) заменены порядком инстанцирования с реактивным отслеживанием (D14, §7.3).
- Добавлен раздел о способе написания кода: слои, пути, срезы, программа для входов (D15, §13).
- `require` дополнен SFINAE-блоками внутри тела (§5.4); связывание имён в полиморфном коде — в момент вызова (§5.3).

**v0.1 → v0.2:**
- Вместо AOT-компилятора с опциональной VM — VM без AOT (D1, D8).
- Вместо алгебраических эффектов — отдельные встроенные механизмы (D6).
- Вместо структурных типов и `A|B` — типы-теги, утиный полиморфизм, расщепление контекста (D4).
- Вместо `inline fn` по требованию — инлайн по умолчанию (D10).
- Вместо мутации compile-time в пределах модуля — глобальная, с моделью порядка (D5, §7.3).
- Вместо текстовых файлов — база AST (D7).
- Синтаксис — (D3).

## 1. Цели и принципы

### 1.1. Цели
1. **Язык — семантическое представление,** программа живёт в VM как данные, доступные ей самой (DP9, DP11).
2. **Базовый язык описывает любой язык:** синтаксис, операторы и конструкции задаются кодом на языке (DP10).
3. **Полиморфизм через инстанцирование:** код по умолчанию — шаблон, специализируемый под фактические типы и значения (DP2, DP6).
4. **Одна семантика compile-time и runtime** (DP1).
5. **Семантический инлайн по умолчанию** (DP4).
6. **VM, владеющая всеми программами:** закрытая система типов, без ABI между программами, статическая изоляция, внешнее управление ресурсами, дамп и восстановление (разбор §2.10).
7. **Реактивный инкрементальный мир:** любое изменение программы инвалидирует только зависимое, в том числе в работающей VM (live-патчинг) (DP17).
8. **Производительность достижима:**. Горячий код специализируется до машинного кода без остаточной динамики.

### 1.2. Не-цели v0.3
- Исполнение без VM (AOT-бинарь). Решено D1.
- Совместимость с существующими языками на уровне синтаксиса. Импорт C — только на границе VM (§11).
- Пакетный менеджер: зависимости — части общей базы AST (§9).

### 1.3. Принципы
| # | Принцип |
|---|--- |
| П1 | База максимально мощная, ограничения — поверх |
| П2 | Семантичность: у каждой конструкции смысл в модели, оптимизации — «сверху» |
| П3 | Не терять информацию |
| П4 | Типы выводятся из логики |
| П5 | Макросы — признак дыры |
| П6 | Нормальное поведение — всегда, без частных случаев |
| П7 | Никаких first-class заплаток под отдельные фичи |

## 2. Архитектура

```
┌──────────────────────────────── VM ─────────────────────────────────────┐
│  База AST (семантическое представление всех программ, key ⇒ узел)       │
│    ▲ правки (семантические операции)      ▲ проекции (текст, дерево…)   │
│    │                                      │                             │
│  Элаборация: синтаксис кодом → ядро → типы/инстансы (реактивно, §10.1)  │
│    │                                                                    │
│  Интерпретатор ядра (эталон; весь compile-time; холодный код)           │
│    │  горячие пути, известные типы                                      │
│  Специализатор → кодогенераторы операций → машинный код (JIT)           │
│                                                                         │
│  Процессы/программы: общая закрытая система типов, статическая изоляция,│
│  файберы, внешнее управление ресурсами, дамп/восстановление             │
└─────────────────────────────────────────────────────────────────────────┘
        хост-ОС (Linux/…) — временно; 
```

**Как решается P1**:
1. Интерпретатор исполняет **любую** программу, в том числе полиморфную без предела, поэтому семантика определена всегда.
2. Специализатор строит машинный код для конкретных *наблюдаемых* типов и compile-time значений. Это ровно то, что VM знает, а AOT-компилятор знать не может.
3. Если специализация не сходится (бесконечный рост типов, бюджет), путь остаётся в интерпретаторе или получает диспатч по `typeid`. Это не ошибка; уровень статичности функции это показывает (§12.3), а VM — причину (§13).

Схему подтверждает практика: так работают Truffle/Graal и Julia (разбор §11.3). Автор пришёл к ней сам: «Я предлагаю интерпретатор как базу»,.

## 3. Семантическое представление и ядро

### 3.1. База AST
- Программа — граф **узлов** в базе VM. У каждого узла стабильный **ключ**: сущности верхнего уровня адресуются по имени модуля и имени, внутренние узлы — по родителю и позиции.
- Ссылки между узлами — **связи**, а не имена в тексте. Переименование сущности меняет одно поле, а не все места использования.
- Изменения программы — **семантические операции** над базой: создать, заменить или удалить узел, перепривязать связь. Текстовый ввод — одна из операций: «разобрать этот текст в этот узел» (§4).
- База персистентна и версионируема: каждое изменение — транзакция с идентификатором, есть история и ветки (замена git для программ в VM, §9.4).

### 3.2. Ядро (базовый язык)
Всё остальное раскрывается в эти формы:

| Форма | Смысл |
|---|---|
| `литерал` | Число, байты, строка |
| `идентификатор` | Связь с объявлением |
| `объявление` | Ввод имени: переменная, функция, тип, оператор. Всегда явно помечено (§4.3) |
| `блок { … }` | Область видимости; значение — последнее выражение |
| `применение f(args)` | Вызов с семантикой инлайна там, где это возможно (§6) |
| `if(c) a else b` | Развилка; расщепляет полиморфный контекст (§5.5) |
| `loop { … }` | Цикл; `break`, `continue` — второй путь выхода, его ловит ближайший `loop` в цепочке встраивания (как `throw` — `catch`, «просто jmp») |
| `return / throw` | Выход из функции / статическое исключение (§8.1) |
| `intercept(тело, блоки)` | Перехват второго пути: первый блок, чей параметр принимает тип брошенного значения (§8.1) |
| `is_index(k, xs)` | Проверка `0 <= k < xs.size`, после которой `k` — безопасный индекс `xs` (§12.1) |
| `ct { … }` | Требование вычислить при компиляции (§7.1) |
| `quote { … }` / `#x` | Код как значение и вставка в него (§7.4) |
| `native "id" { … }` | Вставка на другом языке, выполняемая VM-хостом, — это `cpp {}` автора (§3.3) |

`for`, `while`, `match`, `try/catch`, операторы, методы, `struct`-синтаксис — библиотеки на ядре. Сами операторы — тоже сущности. **Сделано:** `for`, `while`, `try/catch` — прелюдия на языке (`lib/prelude.tz`, встроена в сборку VM и парсится первым модулем базы), §4.4.

### 3.3. Мутируемый интерпретатор (бутстрап)
**Модель .**
- *Компилятор — интерпретатор базового языка с живым состоянием.*; «живая система типов есть только в интерпретаторе… глобальный анализ он в интерпретаторе, он всё знает»; «жит всегда является оптимизацией… влиять ни на что не может». Здесь: разбор `check` раскрывает типовой слой в экземпляры, JIT — только оптимизация с откатом в интерпретатор.
- *Расширение — код на языке, исполняемый этим интерпретатором, а не вызов хоста.* `syntax`, `operator`, конструкции с expr-параметрами, контексты, `emit`, ct-состояние (, тест 108); доступ к коду — узлы AST значениями (`code`, §7.4), не токены и не строка: «токены никаким образом не отличаются от текста… гигиена делается на уровне анализа кода в контексте программы» (, о прок-макросах Rust как `govno.so` с `string govno(string)`). Поэтому процедурного синтаксиса «(токены) → код» и подгрузки собранного C++ (`.so`) нет.
- *Хост — C++, только как бутстрап.*;. Но язык не «поверх хоста»: «настоящий язык, а не вм-параша где всё делает хост-язык цпп. в случае с полноценным языком у тебя нет хост-языка»; API сбоку. Поэтому отражение (`fields`, `attrs`, `emit`, `static_level`, `code_*`) — операции базового языка, известные разбору; `native` — только реализации примитивов хостом (форматирование, разбор чисел), для анализа — граница:  — «не доказано».
- *Цель — «сам хост»:* примитивы (числа, массивы, память) описываются языком, C++ вытесняется (M6). Представление значений интерпретатора (общий `value`) — свойство интерпретатора, работающего, не семантика языка: экземпляры — по типам, перегрузка — по настоящим типам.

.
- `native "cpp" { … }` (вставка значений — `#a`) — фрагмент на C++26, **скомпилированный в сборку VM** (не в рантайме), который регистрирует в VM новые примитивы: операции, представления типов, кодогенераторы. Внутри доступны параметры окружающей функции как объекты VM (`#a` в примере автора `f(a, b) { cpp { #a #b } }`).
- **Сделано (2026-09-30):** `f(…) => native "cpp" { … };` — тело функции на C++ как есть; `#x` — параметр `x` значением VM (`value`), доступны `vm` (интерпретатор) и `where`. `tz native <заголовок> [файлы]` вынимает тела прелюдии (и данных файлов) в `out/native.hpp`, `build.sh` собирает VM и, если заголовок изменился, собирает второй раз; ключ примитива — имя и типы параметров. Машина процессов зовёт тот же примитив через перенос значений. Неизвестный при разборе аргумент — тело само возвращает стёртое значение (как встроенные); рт-результат `native` — «не доказано» в уровне статичности (не тип исключения). Не собранное в VM тело — ошибка «пересоберите». Перенесены из C++ интерпретатора в прелюдию: `text_hex`, `text_fixed`, `parse_int`, `text`, `fill` (native), `is_err` (язык); отражение (`emit`, `attrs`, `fields`, `static_level`, `code_*`) — операции базового языка, не native; в ядре — операции операторов, `print`/`read_floats`, чистые для JIT (`range`, `zero`, `typeof`, `f64`, `i64`, `is_index`), `intercept`, сервисы потоков/сети/файлов/процессов. Символ `'c'` — байт `i64` (нужен и C++-фрагментам). *Моё:* синтаксис `native "cpp" { … }` только телом функции, ключ по сигнатуре, двухшаговая сборка (тесты 106, 107).
- Это механизм бутстрапа: стандартная библиотека и синтаксис пишутся на языке поверх примитивов, введённых `native`. По мере самохостинга (§16) `native "cpp"` заменяется кодом на языке.
- `native` не делит код на «безопасный» и «доверенный» (§12.1): эффекты `native` для анализа — «не доказано», со всеми проверками; то, что функция содержит `native`, выводится и видно в её сущности.

### 3.4. Мутабельность
Переменные мутабельны по умолчанию. `const` — свойство, добавляемое к имени или типу, и по нему тоже есть полиморфизм.

### 3.5. Нет UB
Каждая операция ядра либо имеет определённый результат, либо бросает определённое исключение (`Fault`). Предположения для оптимизации — только явные `assume` (§10.2).

## 4. Текстовая проекция и синтаксис

### 4.0. Текст — проекция, а не язык 
- **Два представления кода:**. Язык — семантическое представление;. Поэтому источник истины — база AST (§3.1), текст — проекция.
- **Но человеку текст нужен:**. Языки поверх JSON/XML и Lisp («текстовое представление данных») — отказ от синтаксиса и парсера. Проекций может быть несколько.
- **Правка — семантическая:**; редактор работает с AST, как KDevelop, LSP — суррогат; программа — слои/пути, а не плоский текст. См. O16.
- **Связи, а не текст:** макросы, `#include`, строковые миксины, текстовые атрибуты — работа с текстом без семантики, костыли; нужны связи между сущностями. Форматные строки — конструкция языка с типами, а не подстрока, см. O17.
- **Данные:** строки — байты; кодировка исходника; структуру текста задают ASCII-разделители, юникод нужен узкому классу задач. Логи и хранение — бинарные: «цена записи бинаря — ноль», текст — только для человека; журнал базы — бинарный (§3.1). Конфиги — на языке с типами, а не YAML/JSON.

### 4.1. Разбор
.

**Лексика:**
- парные разделители ` [ ] { }`;
- литералы: строки `"…"`, символы `'…'`, числа;
- идентификаторы;
- **операторные символы — всегда одиночные** (`+ - * / % < > = ! & | ^ ~ ?.,; @ # $ \`). Многосимвольные операторы (`==`, `=>`, `<=`) — это определённые в библиотеке **последовательности** односимвольных, без пробелов между ними;
- комментарии `//` и `/* */`.

**Фаза 1 — блоки.** Текст режется на дерево парных блоков. Это получается для любого текста; при несбалансированной скобке блок закрывается по отступу и помечается.
**Фаза 2 — операторы.** Внутри блока последовательность токенов сводится к единственному разбору по правилам операторов, действующим в области видимости (§4.4).
**Любой текст — корректная программа базового языка.** Неразбираемый фрагмент становится узлом `Hole` с причиной. Ошибки — это нарушенные инварианты конкретных операторов и конструкций, а не.
**Локальность.** Изменение внутри скобок инвалидирует только эти скобки.

### 4.2. Функции
```tz
add(a, b) => a + b;                       // выражение-тело
norm(v) { return sqrt(dot(v, v)); }  // блок-тело
f64 dist(Point a, Point b) => norm(a - b);// тип результата слева — ограничение
f(1) dyn { … }                            // перегрузка по значению (§5.4)
f(i32 x) { … }
```
- Объявление функции — форма `имя(параметры) тело`. На верхнем уровне модуля и в теле типа она однозначна.
- **Внутри блока** функция с телом-выражением пишется так же: `sq(x) => x * x;` (вызов с `=>` выражением не бывает); с телом-блоком — с типом слева (`i64 sq(x) { … }`), иначе `sq(x) { … }` — вызов с хвостовым блоком.
- Параметры без типа полиморфны: `add(a, b)` принимает всё.

### 4.3. Переменные
```tz
x = 10;                  // объявление с выводом типа: имени x в области нет
x = x + 1;               // присваивание: имя есть
i64 n = read_int;      // тип слева — ограничение и всегда новое объявление (тень)
const name = "z";        // квалификатор — объявление, тип выводится
&e = v[0];               // ссылка на элемент (§12.1)
struct { i64 x = 123; } obj;   // анонимный агрегат по месту
p = {x: 1.0, y: 2.0};    // анонимный структурный литерал
```
**`auto` нет** (решение 2026-09-28): «на самом деле auto ненужно, потому как auto — это непонятно что. В качестве аргумента функция должна мочь принимать всё»;. Поэтому: `x = e` объявляет `x` в текущем блоке, если имени нет в области, иначе присваивает; тип или квалификатор слева — всегда объявление. Параметры и имена блоков — просто имена: `f(xs)`, `for(x: xs)`, `catch(e)`, `catch(T e)`. *Моё:* ссылка — `&e = v[i]`.

### 4.4. Операторы и конструкции кодом
```tz
// операторы — сущности; объявление повторяет запись, приоритетов нет
[[associative]] operator (a) + (b) => add(a, b);
operator (a) - (b) => sub(a, b);
operator -(a) => neg(a);                     // префикс
operator (mut i64 a)++ { a += 1; }           // постфикс
operator (vec a) + (vec b) => vec{a.x + b.x, a.y + b.y};   // перегрузка своим типом

// новая конструкция — просто функция: блок-аргумент + семантический инлайн (§6)
unless(c, expr body) { if(!c) body; }
unless(ready) { wait; }         // хвостовой блок = последний expr-аргумент
```
- **Конструкции кодом (сделано).** «Блоки могут вводить идентификаторы, но в целом они просто блоки вне зависимости от управляющей конструкции. Поведение if/for/fun — не отличаются… Как максимум оно может ввести на уровне конструкции какие-то идентификаторы»;. Синтаксис вызова берётся из объявлений в области (прелюдия — первой):
  ```tz
  while(expr c, expr body) { loop { if(!c) break; body; } }
  for(xs, expr body) { … body(xs[k]); … }                 // for(x: xs) тело
  try(expr body) catch(expr... handlers) => intercept(body, handlers);
  when(c, expr yes) otherwise(expr no) => if(c) yes else no; // своя клауза
  ```
  - **Клаузы:** `try(…) catch(…)` в объявлении — одна функция; параметр клаузы помечен её словом. В вызове `try { … } catch(E e) { … } catch(e) { … }` клаузы сопоставляются с объявлением; повторяющаяся клауза (`expr... hs`) — один аргумент-пак.
  - **Блоки вводят имена:** имя в скобках вызова — `x: xs`, `E e`, в клаузе-блоке и просто `e` — не выражение, а параметр хвостового блока; `: xs` ставит источник аргументом на своё место. `body(v)` в конструкции встраивает блок с `x = v` в контексте того, кто его написал: `return` и `break` из блока идут дальше (семантика инлайна, §6.1). Выражение в скобках клаузы-блока (`catch(e + 1)`) — ошибка разбора.
  - **Хвост:** блок — у любого вызова; инструкция (`while(c) x += 1;`) — у конструкции (последний параметр головы `expr`) в начале инструкции; голова без скобок (`try { … }`) — у конструкции с единственным `expr`-параметром головы.
  - **Цикл в разборе `check`:** итерации с известным исходом исполняются; как только выход зависит от рантайма, ячейки, которые меняет итерация, стираются до типа и тело разбирается до неподвижной точки. Ячейки собираются по записям (журнал ячеек), а не по именам в тексте — так видны и записи блоков конструкций. Вложенные экземпляры одной конструкции с разными блоками — разные экземпляры, а не рекурсия.
- **Операторы кодом (сделано, расширения шаг 3).** «с оператором всё просто. Есть кейворд operator, а далее символы… оператор всегда односимвольный… используя правила описанные для операторов — свести выражение к единственно правильному варианту. Пока что перебором». Все операторы — объявления прелюдии; тело из одного встроенного примитива над параметрами (`add(a, b)`) — операция VM, её исполняют напрямую интерпретатор и машинный код.
  - **Объявление повторяет запись:** параметр стоит на стороне своей ветки («брать левые/правые ветки», там же): `operator (a) + (b)`, `operator -(a)`, `operator (a)++`. Сущность — функция `infix+`, `prefix-`, `postfix++`, перегружается как любая: `operator (vec a) + (vec b)` вызывается, если его параметры принимают типы операндов, иначе — встроенная операция.
  - **Символы:** операторный символ — один; многосимвольный оператор — склеенная (без пробела) последовательность, объявленная в библиотеке. Склеенный ряд режется на объявленные символы ролей «постфиксы, инфикс, префиксы»; подходит ровно одно разбиение, иначе ошибка «разделите пробелом».
  - **Приоритетов нет** (решение 2026-09-28: «только перебор»). Цепочка с несколькими деревьями (`i % 2 == 0`, `x = a + b` — нет: присваивание вне цепочки) — узел `n_chain`; дерево выбирается **при инстанцировании**: все разборы, где каждый оператор инстанцируется (SFINAE по типам); подходит один — он, несколько — ошибка «расставьте скобки», ни одного — ошибка с причиной. `a + b * c`, `a - b - c` на числах — ошибка: нужны скобки. Разбор считает отдельный интерпретатор-проба в режиме разбора — по типам, без вычисления операндов (`i < n && xs[i] > 0` не вычисляет `xs[i]`) и без побочных эффектов; кэш — по типам свободных имён цепочки; машинный код берёт дерево своего контекста встраивания.
  - **`[[associative]]` — инвариант из логики** («вывод инвариантов из логики», там же): одинаковый ассоциативный оператор подряд (`a + b + c`, `p && q && r`) — одно дерево.
  - *Моё:* префиксный и постфиксный операторы — часть своего операнда (`-a * b` — это `(-a) * b`, перебор — только по инфиксам); присваивание `= += -= *= /=` — форма ядра над цепочкой, не оператор; печать ставит скобки везде, где без них разбор дал бы другое дерево.
- **Контекстные условия (сделано):** `[[inside(g)]] f(…)` — сущность существует только в блоках конструкции `g`: «мне нужно, чтобы он существовал, допустим, внутри блоков, которые вызываются… и в struct govno { return 123; } — это не должно работать». Проверяется по месту вызова в тексте (блок, хвост или клауза вызова `g`, до границы функции); вне — ошибка.
- **`syntax`-сущности (сделано 2026-09-30).** «язык - это некий, чтобы понятно было, декларативный описатель его парсера/семантического анализатора. т.е. каждая следующая строчка описывает то как разбирать следующую»;. Объявление повторяет запись, как у `operator`: `syntax repeat {body} until(expr c) => loop { body; if(c) break; };`, `syntax swap(expr a) <-> (expr b) => { … }`. Элементы записи — слова, склеенные символы, `(параметр)` (режим — как у параметра), `{имя}` (блок, expr). Сущность — функция с именем первого слова; использование — вызов с узлом объявления (печать восстанавливает запись); разбор пробует объявления с этим первым словом, последнее — первым; действует со следующей строки. Семантика — обычный вызов с семантическим инлайном: интерпретатор, машина, `check`, JIT без изменений; запись в expr-параметр — запись в место вызывающего (`a = b` в `swap`). *Моё:* первое слово — голова. Процедурная логика формы — на языке в её теле: expr-параметры — код вызывающего, `code(x)` — его AST (§7.4), окружение вызова (O4); не «(токены) → код» (§3.3, тесты 105, 109).

### 4.5. Прочая проекция
- `if(…)`, `while(…)`, `for(x: xs)` — скобки обязательны.
- `;` разделяет выражения в блоке.
- `a.f(b)` ≡ `f(a, b)`, если у `a` нет поля `f`.
- Тип результата функции справа (`-> T`) **не поддерживается**. Если тип результата нужен, он пишется слева.

## 5. Типы

### 5.1. Тип — это тег
.
- Каждый тип — **значение** compile-time вида `type` с уникальным идентификатором. В закрытом мире VM (§2) это число: `typeid(T)`, одинаковое для всех программ в VM.
- **Именованные агрегаты номинальны:** `struct Point {f64 x; f64 y;}` и `struct Vec2 {f64 x; f64 y;}` — разные типы.
- **Анонимные агрегаты** (`{x: 1, y: 2}`, `struct {…} obj`) идентифицируются своей структурой: одинаковые поля — один тип.
- **opaque:** `opaque meters = f64;` — физически `f64`, логически отдельный тип с явным преобразованием.
- Представление вторично.
- **Массив и тапл — одно понятие.** Литерал с элементами разных типов — тапл: `array{1, 2.0}` имеет тип `tuple<i64, f64>`; тапл, у которого в рантайме один тип, — массив `array<T>`. Индекс, известный при компиляции, даёт точный тип элемента; рантайм-индекс расщепляет продолжение по типам элементов (`foo => [T0 => bar, T1 => bar]`, §5.5). Рантайм-смесь — явный вариант.

### 5.2. Value-подход: типы — значения, значения — в типах
- `typeof(e)` вычисляет тип выражения, **исполняя** его compile-time часть и стирая рантайм-значения: `typeof(f(x)) == f(x)` со стёртым рантаймом. Это `type::eval`.
- Типы передаются, возвращаются, хранятся в compile-time переменных и сравниваются: `T = typeof(p); if(T == Point) …`.
- **Значения в типах.** Любое значение, известное при компиляции, может быть частью типа: `array<i32, 3>`, `value(10)`. Вызов функции с compile-time аргументом специализируется по его значению, `value!10`-подход встроен.
- **Логика из типов и типы из логики:** одна функция работает на обоих уровнях.

### 5.3. Полиморфизм — инстанцирование
- Параметр без типа полиморфен. Функция — шаблон; тело **инстанцируется** под фактические типы и compile-time значения каждого применения, поэтому все свойства конкретного типа доступны.
- Никаких объявлений интерфейсов и трейтов: `draw(x) { x.draw; }` работает для любого `x`, у которого есть `draw`.
- Ошибка внутри инстанцированного тела — ошибка **в месте использования** с полным трейсом инстанцирования (§13.4): «ошибки снизу», а не.
- **Табличный полиморфизм** (vtable, интерфейсы) — не механизм языка, а библиотечный паттерн поверх `variant`/таблиц функций, когда он нужен явно.
- **Связывание в момент вызова.** Имена в полиморфном теле (перегрузки, операторы, расширения) разрешаются в контексте **инстанцирования**, а не только определения. Расширения, видимые в месте вызова, участвуют в выборе.  в скриптовых и ФП-языках «связывание происходит в момент определения, а не вызова», а в нормальном языке — наоборот. Это же источник мутации семантики (§7.3).

### 5.4. Ограничения — предикаты
```tz
f(x) { require(typeof(x) == i32); … }   // inline-предикат
odd_small(x) { require(x % 2 == 1 && x >= 1 && x <= 10); … }
f(1) dyn { … }        // перегрузка по значению
f(x) { … }
```
- `require(p)` в начале тела — **ограничение кандидата**. Если `p` при инстанцировании статически ложен, кандидат **исключается из перегрузки** (SFINAE-блок). Если `p` не вычислим статически, кандидат остаётся, а `p` проверяется в рантайме как `assert` (§7.1).
- `require` вне начала тела — обычная проверка (статическая или рантайм).
- **SFINAE-блоки** внутри тела.
```tz
serialize(&out, v) {
  try_compile { out.write_fast(v.raw_bytes); return; }   // исключается, если не инстанцируется
  for(f: ct fields(typeof(v))) serialize(out, v.[f]);
}
```
  Блок `try_compile { … }` исключается целиком, если его содержимое не инстанцируется для текущих типов. Причина исключения доступна в трейсе и в инспекторе, а не теряется молча.
- **Частичная кастомизация конкретной функции.** Перегрузку можно добавить **к конкретной функции** по ссылке на её узел, а не по имени. В проекции: `&serialize(auto, point) { serialize(auto out, point p) { … } }` (без ключевого слова, как расширение `Имя { … }`), где `&serialize(…)` — ссылка на узел по сигнатуре (типы параметров, `auto` — без типа), выбранная редактором (§13.3). **Сделано (2026-09-30):** решение автора — перегрузка к узлу: функции внутри — перегрузки сущности цели под её *текущим* именем, выбор — обычная специфичность; ссылка хранится номером узла (не ребёнок), правки в редакторе сохраняют номер — переименование цели расширение переживает, его проекция обновляется у всех клиентов (тест `82_editor_extend_ref.wire`); нет функции с такой сигнатурой или их несколько — дыра с причиной; слияние переносит расширение и разрешает ссылку в своей базе. JIT берёт перегрузки из таблицы разбора (видит и расширения). Формат базы — `TZDB0006`.
- **Приоритет перегрузки:** из подходящих кандидатов выбирается самый специфичный. A специфичнее B, если предикаты A статически влекут предикаты B. Импликация проверяется в разрешимом фрагменте (§5.7). Несравнимые кандидаты — ошибка неоднозначности с перечнем всех кандидатов.
- `f(1) dyn {}` — сахар для `f(auto x) { require(x == 1); … }` с диспатчем в рантайме, если значение не известно статически.
- Предикат — значение: его можно создать, передать, сохранить и составить через `&&`/`||`, чего концепты C++ не умеют.

### 5.5. Развилки расщепляют полиморфный контекст
; `if(bool)` — «сплит» мономорфного контекста.
```tz
x = if(c) "text" else 42;   // x — ПОЛИМОРФНАЯ переменная: {str | i32} по ветке
x.print;                       // инстанцируется для str и для i32
y = x.len;                // ошибка инварианта в ветке i32: у i32 нет len
```
- Если ветки `if` дают разные типы, **продолжение** до конца области видимости переменной (или до точки слияния) исполняется в **расщеплённом контексте**: каждая ветка продолжается со своим типом. Это не значение типа «A или B»: тип каждой ветки точный.
- **Материализация.** Если значение из расщеплённого контекста нужно сохранить туда, где нужен один тип (поле агрегата, элемент контейнера, аргумент `outline`-функции, переменная, переживающая слияние), создаётся `variant<…>` — библиотечный тип с тегом. Работа с ним — `visit` с перегрузкой.
- Ветки, заканчивающиеся `return`/`throw`/`break`, в расщеплении не участвуют.
- **Цена.** Расщепление N независимых развилок даёт до 2^N продолжений. VM специализирует только **наблюдаемые** комбинации (§10.3), а интерпретатор исполняет любые. Это и есть «VM/JIT вместо компиляции».

### 5.6. Мутация типа (typestate)
 «там даже не столько мутация типов полноценная нужна, сколько **мутируемый constexpr**… struct ref {mut constexpr c = 1; ~ref {—c;} f {static_assert(c != 0); }}… Разрушающий мув это сабсет неразрушающего… пусть будет **hide self**… после вызова этой функции self исчезает из области видимости». Решение (2026-09-28, сделано — M2b):
```tz
struct file { i64 fd; ct bool open = true; }   // ct-поле — состояние при компиляции
close(mut file f) { f.open = false; }
read(file f) { require(f.open); f.fd }

f = file{3};
close(f);
read(f);            // ОШИБКА при компиляции: кандидат read — require не выполнено

send(own msg m) => m.id;
send(m);
print(m.id);        // ОШИБКА: имя m скрыто (own), трейс — где
consume(mut msg m) { hide m; }   // hide self: скрыто имя вызывающего
```
- **ct-поле** агрегата — «мутируемый constexpr»: его значение всегда известно при компиляции (запись рт-значения — ошибка), стирание до типа его не трогает, операции меняют его обычным присваиванием, `require` проверяет — ошибка при компиляции с трейсом. Отдельного синтаксиса пост-типов нет.
- **Смена типа** значения — запись в параметр-алиас значения другого типа (`to_int(mut v) { v = parse(v); }`); `becomes T` не нужен.
- **`hide x`** — примитив ядра: имя исчезает, любое упоминание (чтение, поле, передача) — ошибка с местом скрытия; присваивание целиком возвращает имя. `hide` параметра-алиаса скрывает имя вызывающего (hide self). **`own`-параметр** — явное перемещение: значение уходит в функцию, имя вызывающего скрыто. Неявного «последнее использование = перемещение» нет.
- **Разные состояния по веткам** (решение 2026-09-28: расщепление): ветки рт-`if` разбираются от одного состояния, записанные ячейки сливаются; разные состояния или типы — альтернативы, продолжение расщепляется (§5.5), ошибка — в пути, где состояние не подходит, с этим путём в трейсе (`в пути [g: file{fd: 1, open: false}]`). *Попутно исправлено:* до M2b разбор не сливал состояние переменных после рт-`if` (значение последней ветки считалось известным).
- *Моё:* ct-поля — скаляры и строки; скрытие и ct-состояние — только при компиляции, машинного кода не дают.

### 5.7. Границы разрешимости
- **Разрешимый фрагмент** для импликаций предикатов и статических проверок: линейная целочисленная арифметика и диапазоны, равенства, `typeof(…) == T`, проверки наличия членов (`has(x.f)`, `can(x + y)`), логические связки.
- Предикат вне фрагмента вычисляется, если его аргументы известны при компиляции; иначе он проверяется в рантайме. В перегрузке такие предикаты несравнимы.
- Обратный вывод (по результату найти тип аргумента) не выполняется.
- **Согласованность compile-time и runtime (P18,).** Выбор перегрузки, сделанный при компиляции, обязан совпадать с выбором интерпретатора на тех же значениях. Поэтому если выбор статически не определён однозначно, он **откладывается в рантайм**, а не делается «наугад». Сравнение типов в compile-time и RTTI в рантайме дают одинаковый результат, потому что `typeid` один и тот же (§5.1). Это закрывает причину ловушки: в C++ RTTI работает на строках, а здесь — на тех же числах.

### 5.8. Числа
- `i8…i64`, `u8…u64` — модульная арифметика (как железо, fwrapv —); `f32`, `f64` — IEEE 754.
- Контекст `checked { … }` переопределяет арифметику: переполнение → `throw Overflow` (§8.2; `safe( => …)` автора).
- Числовые литералы полиморфны до инстанцирования. Преобразования без потерь неявные, остальные явные.
- **Уровни совпадения типа (сделано 2026-09-30, решение автора):** «"тип равен" и "значение данного типа может представить входящее значение"… как в перегрузках есть уровни совпадений и выбираем лучшее»; «когда я пишу foo(int) я хочу конвертацию, либо не хочу. Это такой explicit». В параметре и элементе образца `T x` — значение представимо (i64 → f64 без потерь, f64 → i64 целое; значение преобразуется до вызова, экземпляр — в типах параметров), `explicit T x` — только равный тип; точное совпадение — +2 к специфичности, представимое — +1. Все кандидаты отсечены значением — исключение `unpack_failed` («нет перегрузки f для этих значений»); в разборе рт-f64 → i64 — рантайм-перегрузка. Интерпретатор и машина процессов. **Объявление (2026-09-30, *моё* — то же решение):** `f64 x = 3;` — значение приводится, `explicit f64 x = 3;` — ошибка разбора; рт-значение, не представимое в `T` (`i64 a = 2.5` из ввода), — исключение `unpack_failed` (в разборе — рт-проверка). JIT — i64 → f64 только для литерала (тест 101).

## 6. Функции и семантический инлайн

### 6.1. Инлайн по умолчанию
.
- **Правило.** Применение функции с **статически известным вызываемым** (прямой вызов по имени, после выбора перегрузки) **инлайнится**. Исключения: рекурсивный цикл вызовов (раскрывается до бюджета, дальше обычный вызов) и функция, помеченная `outline`.
- **Семантика инлайна** доступна инлайнящимся функциям:
  1. **Адресный `return`.** `return x` выходит из своей функции. `return(f) x` выходит из **внешней** функции `f` в цепочке инлайн-вызовов, `return(caller) x` — из той, в которую заинлайнен вызов;. `return` — оператор (`operator return`), его можно переопределять. В проекции `return(цель)` пишется вплотную; `return (x)` с пробелом — возврат значения `x`. `return` внутри блок- и `expr`-аргументов лексический: выходит из функции, в тексте которой написан
  2. параметры — **алиасы** аргументов вызывающего (§6.2);
  3. `expr`-параметры — **невычисленные выражения**, вычисляемые в контексте вызывающего при каждом упоминании: ленивые аргументы,;
  4. можно возвращать объекты со стека вызывающего;
  5. анализ (исключения, алиасы, типы) локален.
- **Детерминизм.** Семантика не зависит от решений оптимизатора. Функция, которая **пользуется** адресным `return` (п. 1), `expr`-параметрами (п. 3) или объектами со стека вызывающего (п. 4), получает выводимое свойство `inline_required`. Её применение, которое нельзя заинлайнить (через указатель на функцию, как значение, рекурсивно, в `outline`-контексте), — **ошибка** с трейсом, а не тихая смена поведения.
- `outline f(…) { … }` запрещает инлайн: функция становится обычным вызовом с ABI VM, получает собственный адрес и может использоваться как значение. Для `inline_required`-функций `outline` — ошибка.
- Функции, не пользующиеся семантикой инлайна, можно использовать как значения. VM инлайнит их по своему усмотрению, потому что для них это ненаблюдаемо.

```tz
try(expr e) {                  // inline_required: адресный return
  r = e;
  if(r.is_err) return(caller) r;   // выход из load, а не из try
  r.value
}
load(path) {
  text = try(read_file(path));
  cfg  = try(parse(text));
  cfg
}
operator (expr e)? => try(e);               // «расто-макака try» без макроса; сделано — прелюдия, кадр оператора прозрачен для return(caller)
```

### 6.2. Параметры
| Запись | Смысл | По умолчанию |
|---|---|---|
| `x`, `auto x`, `T x` | **Алиас** места вызывающего, без копирования. Функция может его менять без пометки — «конст по дефолту» не навязывается. Меняет ли функция параметр, **выводится** (напрямую, через вызовы, через рекурсию) и видно в отчёте `check` («выводимая из контекста значения семантика»). Не хочешь изменений — передай копию | **да** |
| `mut auto x` | Необязательная явная пометка «меняет». Одновременные алиасы разрешены («опасное-безопасное»); опасные сочетания ловит анализ (§12.1) | |
| `own auto x` | Потребление: объект переходит в функцию, переменная вызывающего завершается | |
| `out auto x` | Конструирование на месте (placement-return) | |
| `expr x` | Невычисленное выражение (только для инлайнящихся функций) | |
| `ct auto x` | Аргумент обязан быть известен при компиляции (`foo(ct x, y)`) | |
| `auto... xs` | Пак (§7.5) | |

. Ссылок как отдельных значений в безопасном коде нет (§12.1): `bar(alias x, alias y)` автора — это поведение по умолчанию.

### 6.3. Замыкания и функции как значения
- Лямбда `(x) => x * 2` — анонимная функция. Если она передана блок- или `expr`-аргументом инлайнящейся функции, она инлайнится и видит контекст вызывающего полностью.
- Замыкание, которое **сохраняется** или **возвращается**, захватывает окружение копией или перемещением (§5.6). Выбор автоматический по использованию; ошибка, если ни один вариант невозможен.
- Функция как значение имеет тип-тег функции (не «указатель на что-то»): у каждой функции и лямбды свой тип, как в C++. Стирание до общего вызываемого типа — только явное (`fn_ref<sig>`).

## 7. Compile-time и метауровень

### 7.1. Стадии выводятся
- Выражение имеет стадию **ct** (вычислимо при компиляции), если все его входы ct и оно не читает рантайм-мир (ввод-вывод, рантайм-память, время). Иначе стадия — **rt**.
- `is_ct(e)` — булева compile-time константа.
- `ct { … }` / `ct e` — требование: вычислить при компиляции или выдать ошибку с трейсом, почему нельзя.
- Функции не размечаются: `add(a, b) => a + b; f(y, z) => add(add(y, 10), z); auto x = 10; f(x, rand)` — `add(x, 10)` свёрнут при компиляции, остаток работает в рантайме.
- `assert(p)` проверяет при компиляции, если `is_ct(p)`, иначе в рантайме. `static_assert` не нужен.

### 7.2. Одна машина
Compile-time исполняет **тот же интерпретатор VM**, что и рантайм. Для VM «компиляция» — это элаборация и специализация внутри одного живого процесса. Поэтому любая функция доступна при компиляции (D11), а согласованность CT/RT (§5.7) обеспечена построением.

### 7.3. Глобальная мутация compile-time состояния
..

**Сущности.**
- `ct auto counter = 0;` — **compile-time переменная**, видимая всем, кто импортирует её модуль, и изменяемая любым compile-time кодом.
- **Расширения.** Любую сущность — тип, функцию, перегрузку, оператор, пространство имён — можно дополнить из **любого** места программы формой `Имя { … }` без ключевого слова: «что-то {} — это расширение сущности… любая сущность это идентификатор сущности и композиция из всех расширений, которые для него определены». `Point { i64 z = 0; [[packed]] }`, новая перегрузка `f(my_t x)`, новый оператор. ODR нет. (В выражении `Point{1, 2}` — создание агрегата; различаются местом.)
- `emit(decl)` — порождение сущности compile-time кодом.

**Модель порядка — порядок инстанцирования** (D14).. Лупхолы C++ — «то, что логически следует из базовой семантики», а не трюк. Здесь они легальны и определены:
1. **Compile-time — это исполнение.** Элаборация программы — исполнение compile-time кода интерпретатором VM в **каноническом порядке инстанцирования**: модули верхнего уровня — в порядке импорта от точек входа; внутри модуля — в порядке узлов; каждое применение полиморфной функции инстанцируется **в точке первого применения**, в глубину, как в C++. Пример автора `const govno = 0; foo; bar; govno == 2` работает буквально: после `foo` и `bar` значение равно 2.
2. **Чтение видит текущее значение** на момент исполнения в этом порядке. Состояние, которое видел инстанс, входит в его ключ: одна и та же функция с одинаковыми типами, инстанцированная при разном видимом состоянии (например, до и после регистрации перегрузки), — это **разные инстансы**. Это «мутация сигнатур» автора без нарушения ODR, потому что ODR нет.
3. **Связывание в момент вызова** (§5.3): инстанс видит расширения, зарегистрированные до его точки инстанцирования.
4. **Детерминизм.** Канонический порядок определяется программой, а не обходом VM. VM вправе вычислять лениво, параллельно и мемоизировать, но наблюдаемый результат обязан совпадать с каноническим порядком. Недетерминированные входы (время, случайность, рантайм-I/O) в compile-time запрещены.
5. **Реактивность.** Каждое compile-time вычисление записывает прочитанные и записанные ячейки состояния. Изменение программы (в том числе в работающей VM) переисполняет, начиная с самой ранней затронутой точки инстанцирования, **только** тех, кто читал изменённые ячейки.: VM разбивает состояние на независимые части по графу чтений и записей.
6. **Конфликты расширений** — две равно специфичные перегрузки, видимые в одной точке инстанцирования, — ошибка с трейсом обоих мест регистрации. `sealed` запрещает расширение сущности вне модуля-владельца (P13).
7. **Библиотечный паттерн «регистрация → финал»** [удобство]: `ct registry<T> r;` + `r.finalized`. Чтение финала откладывает инстанцирование читателя до конца элаборации модулей, которые могут писать в реестр. Это не отдельная модель, а функция поверх пунктов 1–5.

**Сделано (M4, 2026-09-28).** `ct x = e;` — переменная модуля при компиляции (инициализируется при элаборации в порядке модуля; менять — только ct-кодом, иначе ошибка). `ct { … }` / `ct e` в функции исполняется **один раз на экземпляр** — место вызова (контекст встраивания), — и результат этого экземпляра фиксирован: пример автора `govno == 2` и «a и b будут разными» работают буквально (тест `59_ct_counter`). Канонический порядок: при `run` ct-код программы исполняет разбор всей программы (обход в глубину, обе ветки развилок по порядку текста), исполнение берёт его результаты по местам вызова и итоговые ct-переменные — результат не зависит от того, какие ветки исполнились. **Инспектор порядка** — раздел отчёта `check` «порядок инстанцирования (ct)»: место, экземпляр, значение. Функции с ct-кодом — интерпретатор (машинный код без канонического ct — позже). Конфликт равно специфичных перегрузок — ошибка «неоднозначный вызов» с местами кандидатов; `sealed` — пока нет.

**Цена и открытый вопрос (O2).** Порядок инстанцирования делает результат зависимым от того, что инстанцируется раньше. Это та же цена, что у лупхолов C++, но здесь порядок определён и виден в инспекторе (§13). Автор сам признаёт, что опыта таких систем нет.

### 7.4. Сущности компилятора как значения
«в этом суть мета-языка»: `struct foo{}` — экземпляр типа `struct`,.
| Значение | Возможности |
|---|---|
| `type` | `fields(T)`, `size(T)`, `typeid(T)`, построение типов (`make_struct([...])`), `extend` |
| `code` | `quote { … }`, вставка `#x`, обход: `code(x)` — узел выражения (у expr-параметра — код вызывающего), `code_kind`, `code_items`, `code_name`, `code_text` (сделано 2026-09-30, тест 109) |
| `decl` | `decls(module)`, `emit(decl)`, атрибуты как типизированные значения |
| `fn` | Перегрузки как адресуемый набор; `compile_for(f, types…)` → специализированная функция; `residual(f…)` → машинный план для инспекции |
| `scope` | Окружение вызова (сделано 2026-09-30, O4): свободное имя тела функции — у вызывающего и дальше по цепочке вызовов |

- `code` — узлы базы со **связями**, а не текст. Гигиена обеспечена построением: имя в `quote` уже связано с объявлением.
- **Атрибуты — `[[…]]` как в C++, но внутри — значения языка**, вычисляемые при компиляции: `[[role(user), async]] api_call { … }`, читаются `attrs(f)`. Автор сам пишет `[[internal("govno")]]`, `[[dependson(left, right)]]`, а атрибуты-текст ругает; `magic<role<user>, async>` — то же самое через базу.
- **Задача этапа — интероп кода и структур компилятора:** «вот задача текущего этапа — сделать этот интероп между кодом и структурами компилятора/аст. а читать/писать — это минорно»;.
- **Рефлексия агрегатов вместо derive:**
```tz
to_json(v) {
  if(typeof(v) is number) return to_string(v);
  if(typeof(v) == str)    return quote_json(v);
  parts = map(ct fields(typeof(v)),
                   (f) => "\"" + f.name + "\":" + to_json(v.[f]));   // v.[f] — поле по дескриптору
  "{" + join(parts, ",") + "}"
}
```
Одна реализация для всех агрегатов. Цикл по полям раскрывается при компиляции. **Сделано (M4):** `v.[f]` — поле по дескриптору из `fields(T)` (или по имени-строке), известному при компиляции; `to_json` — тест `60_to_json` (перегрузки по типу вместо `is number`).

### 7.5. Паки и агрегаты
- `auto... xs` — пак; пак — **значение** со свойствами (`xs.size`, `xs[i]`, итерация при компиляции), связанное с типами элементов.
- Агрегат ↔ тапл: `to_tuple(agg)` и `from_tuple<T>(t)` встроены (`struct_to_tuple`).
- **Распаковка (сделано 2026-09-30, P12).**. Решения пользователя: образец пишется как конструктор; первые контексты — объявление, условие `if`, параметр. Образец `Имя{…}` (struct — по полям позиционно) или `array{…}`; элемент — имя, `T имя` (проверка типа), `_`, вложенный образец, `(значение)` (равенство), `...остаток` (в `array`, один, в любом месте; остаток — массив). `array{x, ...xs} = e;` — имена в блок, неудача — исключение `unpack_failed` (ловится `catch`; в разборе при рт-длине — рт-проверка отчёта). `if(array{x, ...xs} = e) … else …` — успех — условие, имена только в then. `f(array{})` / `f(array{x, ...xs})` — перегрузка по распаковке: условие кандидата (как ведущий `require`), специфичность — 1 + проверяемые элементы; «рантайм-перегрузки… по значениям»: в разборе кандидаты, чья распаковка зависит от рт-значения, разбираются все по специфичности до первого точно подходящего, итоги сливаются, как ветки `if`; ключ рекурсии разбора теперь включает перегрузку. **Предикат (2026-09-30):** в выражении `образец = значение` — `bool`, имена — при успехе: `require(array{a, b} = xs)` в начале тела — условие кандидата и имена для тела, `(point{u, v} = q) && u < v` в условии `if` (имена условия — только в then); рт-условие ведущего `require` тоже делает перегрузку рантаймовой (разбираются все кандидаты до точного). Интерпретатор и машина процессов (значение-элемент — литерал); JIT — пока интерпретатор. *Моё:* синтаксис элементов, `unpack_failed`, специфичность; ведущий `require` — условие кандидата, не проверка тела: рт-проверку разбор относит к вызову (`unpack_failed`), тело экземпляра — без `require_failed` (тест 100). **Сопоставление = перегрузка:**  — ключевого слова `match` нет; локальные функции одного имени в блоке (`len(array{}) => 0; len(array{x, ...xs}) => 1 + len(xs);`) — набор перегрузок над окружением блока (замыкание), выбор — как у функций модуля, по значению. Разбор: если образцы-массивы из имён/`_`/остатка покрывают любую длину — неудачи нет, иначе рт-проверка `unpack_failed`. Интерпретатор и машина процессов (у машины ведущий `require` локальной функции — без захваченных имён). **Интерфейс распаковки (2026-09-30, решение автора):** «на его внутренние куски? Либо на то что он даёт наружу как интерфейс?… `{10.size}`… в сишке там неявный this». Элемент `.обращение: подобразец` — цепочка от неявного значения (`n_subject`): `.поле`, `.size`, `.f` (функция значения, §4.5), `[k]`: `array{x, ...xs, .size: (3)}`, `point{.y: b}`, `line{.b.y: by}`, `array{[0].x: (0)}`; не-агрегат — только обращениями (`T{.f: …}`). Обращение не удалось (граница, исключение) — не распаковалось (в условии/перегрузке — ложь). Специфичность: точная длина и проверки элементов конкретнее остатка и имён. Машина процессов — поля, `.size`, `[литерал]` (вызовы в образце — пока нет). *Моё:* синтаксис `обращение: подобразец`. Уровни совпадения типов — сделано (§5.8). **Паки:**. Хвост параметров `f(x, ...xs)` — остаток аргументов кортежем (`array`), `T... xs` — каждый элемент представим в `T`; точное число аргументов конкретнее хвоста (+1). ## 8. Исключения, контексты, конкурентность 

### 8.1. Статические исключения
- `throw e` — выход к ближайшему охватывающему `catch`, совместимому с типом `e`.
- **Множество исключений функции выводится** («покраска» по стеку вызовов в пределах `try`). Аннотации не нужны; `nothrow` — выводимое свойство.
- **Реализация.** Там, где `throw` и `catch` связаны инлайном (типичный случай при инлайне по умолчанию), `throw` — это **переход** (`jmp catch_block`), без таблиц раскрутки. Через `outline`-вызовы исключения распространяются кодом возврата, сгенерированным VM. Основной путь бесплатен в обоих случаях.
- `try { … } catch(T e) { … } catch(auto e) { … }` — **выражение**, как `if`; `throw x` — выражение. `catch(T e)` ловит по типу-тегу значения, `catch(auto e)` — любое (база иерархии;), `catch(T _)` — по типу без имени. Бросать можно любое значение, обычно агрегат `http_error{400}`. `try/catch` — библиотечная конструкция над `intercept` (§4.4). `break`/`continue` — не исключения: `catch(auto e)` их не ловит (*моё*: иначе пользовательский catch глотал бы break).
- **Ошибки VM — исключения своих типов:** `out_of_bounds`, `div_by_zero`, `require_failed` (агрегат с полем `message`); их ловит `catch` так же.
- **Реализация M2a (интерпретатор):** второй путь — вид потока, как адресный `return`; в `check` бросок по рт-ветке записывается в сборщик ближайшего `try`, разбор идёт по обоим путям; «покраска» — типы исключений каждого экземпляра, включая ошибки VM на недоказанных местах (рт-индекс без безопасного индекса, рт-делитель, рт-`require`), видны в отчёте. Непойманное — ошибка с трейсом места `throw`.
- Непойманное исключение завершает **файбер** (§8.3) с трейсом; VM продолжает работу (изоляция,).

### 8.2. Контексты
..
- **Контекст** — функция с блок-аргументом, которая при инлайне **переопределяет перегрузки** операций внутри блока:
```tz
checked(expr body) {
  using operator (i64 a) + (i64 b) => add_checked(a, b);   // до конца кадра checked
  body
}
checked { a + (b * c) }
checked { sq(n) }       // * внутри sq тоже проверяется: экземпляр sq[checked]
```
- **Сделано (M2d, 2026-09-28).** `using operator …` в теле функции-контекста — переопределение, действующее до конца её кадра **для всего выполняемого**: текста блока и вызванных из него функций (решение: «на всё выполняемое»;). Выбирается ближайшее переопределение, чьи параметры принимают типы операндов; тело переопределения видит обычные операции. Экземпляр функции специализирован по контексту — `sq(рт i64)[checked]` в отчёте, своя «покраска» (`бросает: overflow`). Это единственный механизм: ни монад, ни системы эффектов.
- `checked` — прелюдия: `+ - *` над i64 с исключением `overflow` (`add_checked`/`sub_checked`/`mul_checked`); вне контекста арифметика модульная (§5.8). *Ограничение:* машинный код в контексте — пока интерпретатор (ключ JIT без контекста).
- Стандартные контексты: `checked` (арифметика с проверкой), `with_alloc(a)` (аллокатор), [E] `on(target)` (кодогенерация под платформу, `amd64( => gen)`).

### 8.3. Конкурентность: файберы и блокирующий API
- `spawn f(args)` создаёт **файбер** — стековую корутину с ленивым стеком. Планировщик — часть VM.
- Весь ввод-вывод **блокирующий** по интерфейсу. Под VM блокирующая операция паркует файбер и отдаёт ядро другому; когда данные доставлены, VM возобновляет файбер. Это push-модель.
- `async/await` **нет** и не будет:,. Функции не делятся на синхронные и асинхронные.
- Параллельное ожидание — библиотечные `join(a, b)`, `select(…)` поверх файберов.
- Генераторы — `spawn` + поток (решение автора 2026-09-29: без отдельного `generate`). **Сделано (2026-09-29): генератор → цикл.** JIT сворачивает пару `s = stream(…); spawn { W }; … for(x: s) B` без файбера: в месте `for` исполняется W, где `write(s, v)` — это B с `x = v`: «оптимизация с преобразованием этих генераторов в циклы… непаханное поле»; «при call/ret свиче… Всё это можно свернуть». *Моё — условия (наблюдаемое не меняется):* W из действий VM только пишет в `s` и последним действием закрывает его, не может упасть, без `return`/`throw` и настоящих вызовов, не пишет наружу; переменные, которые видит W, после `spawn` не меняются; `s` больше не используется, кроме этого `for` (после свёртки поток закрыт и пуст, как после обмена); B не выходит из цикла; `for` — в той же области управления (ветка, тело цикла), что `spawn`. Иначе функция — интерпретатор. Замер: производитель → потребитель 20 000 000 элементов — 0,02 с, как цикл без файберов (тест `79_generator_loop`).
- Данные между файберами передаются перемещением или через каналы. Разделяемая изменяемая память — через `sync`-примитивы (атомики, мьютексы) библиотеки (§12.1).
- **Инвариант через точку блокировки:** алиас, живущий через блокирующий вызов, — кандидат на «опасное-опасное», если объект виден другому файберу, который может его инвалидировать. Анализ §12.1 рассматривает точку блокировки как место, где другие файберы могут выполнить мутации.

## 9. Программы, модули, VM как среда

- **Сделано (M3a, 2026-09-28).** `spawn { … }` — файбер: стековая корутина со своим стеком (страницы хоста, резерв 64 МБ без коммита, защитная страница), переключение — десяток инструкций своего ассемблера (callee-saved регистры и `rsp`, `ret`): «нам нужно сохранить тот самый стек, те регистры… Подменить их… вызвать ret… а создаётся стек в момент создания самой корутины». Интерпретатор и машинный код работают на стеке файбера без изменений; у файбера своё состояние исполнения (кадры, трейс, контексты).
- **Обмен — потоки, не каналы** (решение 2026-09-28): `stream(cap)`, блокирующие `write(s, own x)` / `read(s)`, `more(s)`, `close(s)`, `for(auto x: s)`; тот же вид потока — для сокетов и файлов (M3b). Значение уходит в поток перемещением (`own`); *моё:* скаляр перемещается копией (имя не скрывается).
- Планировщик: очередь готовых; блокирующая операция паркует файбер. Взаимная блокировка — ошибка программы с трейсом места ожидания; непойманное исключение завершает свой файбер, остальные работают, программа завершается с его трейсом; в конце `main` VM ждёт файберы, оставшиеся — раскручиваются (отмена, не исключение языка). В разборе `check` тело `spawn` разбирается на месте, операции потоков — рантайм-эффекты (не сворачиваются), тип элементов потока выводится из записи.
- Замер: 200 000 обменов туда-обратно через два потока — 0,93 с (интерпретатор).
- **Операции потоков в машинном коде (2026-09-29).** `write`/`read`/`more`/`close`/`yield` в JIT — вызов VM; файбер паркуется внутри вызова, на своём стеке, код вокруг остаётся машинным: «в случае с переключением контекста снизу компилятор может оптимизировать код так как будто бы его нет»; «Переключение контекста не является тяжёлым… Это миф». Тип `stream<T>` в JIT — номер потока в регистре; тип элементов — из разбора всей программы по месту создания потока (контекст встраивания + место в тексте; разбор повторяется, пока типы уточняются: тело `spawn` разбирается раньше продолжения). *Моё:* ошибка или отмена файбера внутри операции не раскручивается C++ сквозь машинный код — ждёт в VM, код выходит меткой. `spawn` (замыкание над кадром) — пока интерпретатор. `bench/fibers.tz`, 200 000 операций: пинг-понг 1,03 → 0,03 с, производитель → потребитель 0,65 → 0,01 с (эталон без файберов — 0,00 с). Вход из машинного кода — номер операции и номер потока (`stream_do`), без значения-потока, вектора аргументов и места в тексте (место — только при ошибке).
- **Прямая передача (2026-09-29).** Файбер, разбуженный обменом через поток (запись будит читателя, чтение — писателя), исполняется следующим — раньше стоящих в очереди: его стек и данные ещё горячие. *Моё:* подряд не больше 128 прямых передач — иначе пара файберов отнимет ядро у остальных; `close`, `yield`, конец файбера — обычная очередь. Машина процессов планирует так же (тест `78_handoff`). Попутно в разборе: тело `spawn` разбирается в контексте, где написано (как исполняется), создание потока — рантайм-эффект, значение потока в разборе несёт тип элементов (слияние стирает номер, не тип). Замер (1000 пар файберов, 200 000 обменов, JIT): 0,23 → 0,16 с, без учёта создания файберов — как одна пара; интерпретатор 1,71 → 0,94 с.
- **Сеть и файлы (M3b, 2026-09-28) — поток событий, не сокеты.**;. Поэтому `net = listen(port)` — **один поток событий** `event{peer, kind: "open" | "data" | "close", data}` по всем соединениям; `send(net, peer, data)` — в исходящий поток, без ожидания; `drop(net, peer)`; `c = connect(host, port)` — такой же поток для одного соединения (`send(c, data)`). Файлы: `open(path)` — поток кусков, `create(path)` — запись. Под ними **io_uring** (как в): мультишот `accept` и `recv` с общим кольцом буферов ядра — одна заявка на сколько угодно событий; отправка и файлы — заявки; планировщик, когда готовых файберов нет, ждёт завершений в `io_uring_wait_cqe`. Echo-сервер — один обработчик потока событий (`55_echo`); 200 соединений × 50 обменов — 0,21 с, 19 МБ (на epoll с файбером на соединение было 1,1 с, 44 МБ). `text(x)` — текст значения. Зависимость — `liburing`.

### 9.2. Программы и процессы
- **Программа** — набор модулей с точкой входа `main`. **Процесс** — запущенная программа в VM с собственной памятью и файберами.
- Все процессы в VM разделяют **одну закрытую систему типов** и одну базу кода. Типы передаются между процессами без сериализации имён.
- **Изоляция статическая:** процесс не может получить доступ к памяти другого, потому что безопасный код не умеет порождать ссылки на чужое (§12.1), а обмен идёт через каналы VM с перемещением. Аппаратная защита памяти между процессами не требуется; `native`-код — отдельный вопрос (O14).
- **Внешнее управление.** VM может: запустить, остановить, заморозить процесс; запросить у процесса освободить ресурсы через стандартный протокол `on_pressure`; **задампить** процесс и восстановить его в той же или другой VM. Представление памяти процесса известно VM, поэтому дамп корректен по построению.

- **Сделано (M5): дамп и восстановление.** Процесс исполняет машина процессов: по AST, без рекурсии, стек задач и значений, кадры и области — данные по индексам, значения — по значению. Дамп — журнал базы и эти арены; восстановление в другой VM — новая база из журнала и то же состояние, исполнение продолжается с того же шага.;. Файберы и потоки — тоже данные машины (стеки задач файберов, очередь готовых, буферы потоков): процесс дампится посреди обмена между файберами. *Моё:* ресурсы хоста (сеть, файлы, процессы ОС) машина пока не исполняет — в дамп они не входят.

### 9.3. Горячая замена
- Изменение кода в базе у работающей VM применяется к живым процессам: новые вызовы идут в новую версию, работающие кадры доживают в старой (как в Erlang).
- Изменение **представления** типа живого значения требует функции миграции `migrate(old T) -> new T`. Без неё изменение откладывается до перезапуска процесса.

### 9.4. Версии и обмен кодом
- База AST версионируется транзакциями. Ветки, слияния и дифф — семантические: по узлам и связям, а не по строкам.
- Автоматического слияния нет: конфликт показывается как две разницы,.
- **Сделано (M5):** живая правка — через одно состояние VM, конфликтов нет; разошедшиеся копии базы — трёхстороннее слияние по элементам модуля от общего начала журналов (`tz diff`, `tz merge`, в редакторе — Ctrl+M): изменённое в одной копии берётся само, в обеих — конфликт, оба варианта человеку.
- Обмен кодом между VM — пакет узлов с хэшами содержимого. Сторонний код — это узлы в той же базе, никаких бинарных блобов.
- **Текстовый экспорт и импорт** — для публикации, ревью и работы в обычном редакторе. Экспорт детерминирован; импорт — это разбор (§4.1), связывающий имена с существующими узлами по ключам.

### 9.5. VM как ОС: классы процессов, ядра, сервисы
Источник — ветка. «производительность — она нужна 1-2 активному приложению… то как там работает остальной мусор — нам максимально похрен. Нам нужно обеспечить эффективность там, где она нужна».

**Классы процессов.**
| Класс | Кто | Ресурсы | Переключение |
|---|---|---|---|
| **монопольный** (`foreground`) | 1–2 активных приложения: игра, редактор, сервер. «монопольное приложение, владеющее всем и обслуживающее само все свои потребности» | Выделенные производительные ядра (P-cores / big), закреплённые за процессом; своя память; приоритет в кэше и полосе памяти | Только кооперативное (call/ret между файберами процесса). VM не вытесняет его, кроме аварийного случая (§ниже) |
| **фоновый** (`background`) | Всё остальное: мессенджер, синхронизация, «гуёвый мусор» | Общий пул энергоэффективных ядер (E-cores / LITTLE). Если их нет — остаток ядер с низким приоритетом | Кооперативное внутри пула; мультиплексирование многих процессов в один поток исполнения |
| **сервис VM** | Криптография, сеть, IPC, файловая система, кодеки (см. ниже) | Исполняется в контексте вызывающего (инлайн) или на ядре своего класса | Как у вызывающего |

- Класс назначает VM (автор или политика: фокус окна, явный запрос приложения). Процесс может запросить повышение; монопольных процессов не больше, чем выделенных групп ядер.
- — фоновый пул рассчитан на гетерогенные процессоры. На хост-ОС VM определяет классы ядер (Linux: `/sys/devices/cpu_core` и `cpu_atom` у Intel, `cpu_capacity` у ARM) и закрепляет потоки через affinity.

**Переключение.**. Поэтому:
- Внутри процесса и в фоновом пуле переключение **кооперативное**: файбер отдаёт управление в точке блокировки (§8.3), обе стороны знают о переключении, сохраняется только живое состояние (call/ret-переключение).
- **Принудительное вытеснение** VM выполняет редко — сторожевым таймером, когда файбер не отдаёт управление дольше порога (по умолчанию 10 мс для фоновых, 100 мс для монопольного). «надОС… умеет переключать, включая принудительно. Важно то, что она не делает это сотни тысяч раз в секунду как сейчас».
- Безопасные точки вытеснения — проверки на обратных рёбрах циклов и вызовах, вставляемые JIT. Вытеснение — это кооперативный уход в ближайшей безопасной точке, а не сигнал с полным сохранением контекста.

**Мультиплексирование ввода-вывода.** Блокирующие операции файберов (§8.3) VM собирает в пакеты и отдаёт хосту одним вызовом (Linux: io_uring). Для монопольного процесса — отдельное кольцо на его ядрах, без общих очередей.

**Сервисы VM (системный рантайм внутри VM).**
- Криптография, сеть (TCP/UDP/QUIC), IPC, файловая система, сжатие, кодеки — это **модули VM**, написанные на языке, а не библиотеки, линкуемые в каждую программу.
- Программа вызывает сервис **обычным вызовом**: в закрытом мире VM это та же база кода, поэтому работают инлайн, специализация под типы вызывающего и статические исключения. Нет ни ABI, ни системного вызова, ни копирования буферов: алиасы передаются как есть (§6.2), анализ опор (§12.1) действует через границу.
- **Секреты остаются в сервисе:** ключи — opaque-значения сервиса (§5.1), программа держит дескриптор, а не байты. Сервис разделяет вычислительные ресурсы (аппаратные ускорители, пулы потоков, пакетирование операций) между всеми процессами.
- Обновление сервиса — горячая замена кода в VM (§9.3): одна правка криптографии сразу действует для всех программ.

**Пайплайны между процессами.** «сами подобные инстансы программ могут договариваться между собою об эффективном пайплайне». Каналы между процессами VM (§9.2) — типизированные. Если оба конца специализированы, VM вправе сливать соседние стадии (передача без очереди, в пределе — инлайн стадии потребителя в производителя: слияние проходов вместо раздельных).

**Изоляция без переключения режимов.** «нам на самом деле ненужна изоляция между ядром и юзерпейсом… мы берём несколько программ и мультиплексируем их в одну, изолируя на уровне юзерспейса». Процессы VM живут в одном адресном пространстве хоста; изоляция — статическая (§9.2, §12.1). Аппаратная защита памяти нужна только на границе с `native`-кодом и хостом (§11, O14).

## 10. Движок VM

### 10.1. Реактивная элаборация
- Всё, что VM выводит, — функции-запросы над ключами узлов: разбор блока, связывание, тип выражения, инстанс, стадия, план исполнения, машинный код. Результаты мемоизируются вместе с множеством прочитанных ключей.
- Изменение узла инвалидирует зависимых. Если пересчитанный результат не изменился, распространение останавливается (early cutoff).
- Compile-time вычисления и записи в `ct`-переменные (§7.3) — такие же запросы.
- Редактор и отладчик — клиенты VM, работающие с теми же запросами. LSP — адаптер, а не архитектура.

### 10.2. Оптимизации «сверху»
- Оптимизации работают на **плане исполнения**, который сохраняет семантику ядра: алиасы и их режимы, типы, предикаты, стадии, связь `throw`/`catch`.
- Всё, что в C/LLVM передаётся атрибутами (`noalias`, `pure`, диапазоны), выводится из ядра.
- `assume(p)` — явное предположение для анализа. Оно **проверяется всегда**, кроме мест, где доказано; ложное `assume` — ошибка с трейсом, не UB.
- Оптимизация как **подъём инвариантов**: известные факты распространяются по графу вызовов до неподвижной точки.

### 10.3. Специализатор и JIT
1. **Счётчики.** Интерпретатор считает исполнения путей и собирает наблюдаемые типы и compile-time значения.
2. **Ключ специализации:** функция + типы аргументов + compile-time значения + константность + режимы параметров. Одинаковые ключи — одна специализация.
3. **Расщеплённые контексты** (§5.5) специализируются по наблюдаемым комбинациям. Ненаблюдаемые остаются в интерпретаторе, и JIT вставляет для них выход в интерпретатор.
4. **Сходимость:** на функцию — не более `spec_budget` специализаций (по умолчанию 64). Если бюджет исчерпан или типы растут без предела, для остальных ключей остаётся интерпретатор или диспатч по `typeid`, и VM показывает причину (§13).
5. **Дедупликация** (`compile_for`): специализации с одинаковым машинным планом сливаются.
6. **Кодогенераторы операций.** У каждой операции ядра и каждого примитива, введённого через `native`, есть **кодогенератор** — функция, выдающая машинный код для конкретных типов операндов. JIT склеивает их по плану с распределением регистров..
7. **Деоптимизация.** Если наблюдаемый тип или предикат, на котором основана специализация, нарушается (например, изменили код в базе), кадры переводятся обратно в интерпретатор. Поскольку язык статичен по семантике, деоптимизация нужна только при изменении программы, а не при «неожиданном типе».

### 10.4. Бэкенд
- **Кодогенераторы на языке (сделано 2026-09-30, начало).** «все операции специализируются как кодогенераторы. поэтому какой хочешь кодогенератор - такой и напишешь»; против зашитого в компилятор. Цель — функция-контекст (`amd64(expr body)`, `arm64(expr body)`), в ней `using operator (i64 a) + (i64 b) => array{0x48, 0x1, 0xC8};` — машинный код операции над регистровой моделью JIT (первый операнд — аккумулятор, второй — регистр второго операнда, результат — в аккумуляторе). JIT для операции ищет кодогенератор в базе (любой модуль, в том числе программа) и вставляет его байты; ревизия кодогенератора — в зависимостях экземпляра. Нет кодогенератора на языке — встроенный на C++ (бутстрап). Кодогенератор получает операнды номерами регистров цели (первый — аккумулятор, второй — регистр второго операнда); кодирование — функции на языке (`x64_rr`, `x64_0f`, `x64_shift`, `a64_rrr`, `a64_word`) на битовых операциях `& | ^ << >>` (i64, сдвиг по модулю 64, `>>` арифметический). В прелюдии — `+ - * & | ^ << >>` и сравнения для `i64`, `+ - * /` для `f64` обеих целей (байты x64 совпадают с прежним C++; кодирование склеивается раскрытием `array{...a, …}`); последнее объявление — первым: программа переопределяет прелюдийный без сборки VM (тест 110), статистика JIT называет модуль кодогенератора. Проверка AArch64 в qemu сверяет их. Литерал `0x…`. **Переходы — метки значениями:** машинный код — «Как в асм, плоский код. Есть только всякие джампы и их вариации»; в языке же goto нет. Кодогенератор получает адрес метки смещением от начала своих байтов (`fault` — ловушка, имя из окружения) и сам кодирует переход; JIT вызывает его второй раз, когда метка привязана, и сверяет длину. Так сделаны `/ %` для `i64`: x86-64 — test/je/cmp -1/idiv (INT_MIN / -1 модульно), AArch64 — cbz/sdiv/msub (sdiv не падает). Ветвления тем же способом: в контексте цели — функции `jump` и `jump_unless(bool a)` (смещение `target`); `if`, `loop`, `break`/`continue` берут их из базы (переход назад — смещение сразу, вперёд — второй вызов при привязке метки). Внутри `try` деление — пока C++. Интерпретатор: INT_MIN / -1 раньше падал SIGFPE — теперь модульно. Пересылки и память: в контексте цели — `move`, `load`, `store` и `move_f64`, `load_f64`, `store_f64` (регистры — номера кодировки цели, смещение — число; x86-64 — `[база + disp32]` с SIB для rsp/r12, AArch64 — ldur/stur или x16 + регистровое смещение, от sp — вдвое); все загрузки и сохранения переменных и временных в JIT идут через них (длины кода прежние). Найденные кодогенераторы и их байты кэшируются на время компиляции функции. Элементы массивов (`load_index`, `store_index` и `_f64`: `[база + индекс * 8]`), константы (`load_const`), проверки границ (`check_index` с ловушкой `fault`) — тоже на языке; ловушки внутри `try` — тоже (метки ловушек стабильны). Сравнения f64 (с NaN всё, кроме `!=`, ложно), стек временных (`push_tmp`/`pop_tmp`, `stack_alloc`/`stack_free`), преобразования (`to_f64`, `to_i64`, `move_to_f64`, `move_from_f64`), `negate` — тоже на языке. Кодогенератору доступны имена окружения `acc` и `second` — регистры модели JIT (функции кодирования берут их из окружения вызова, O4). Метки, кадр, вызовы — тоже: `jump_if`, `jump_if_set` (отметка ошибки VM после вызова), `store_const`, `address`, `call_reg`, `call_mem`, `frame_enter`/`frame_leave`/`frame_alloc` (размер — вторым вызовом той же длины)/`ret`, `is_index`, префиксные `!` (bool) и `-` (f64); все привязки меток дописывают переходы языка. **Итог (2026-09-30): с прелюдией C++ сам не пишет в машинный код ничего, кроме адресов хоста** (`mov_addr` — адреса переменных VM и функций хоста; у AArch64 — релокации для проверки в qemu): статистика JIT — «от C++: N байт», N — только эти адреса (0 у функций без ловушек и вызовов хоста). Кодогенерация C++ осталась запасным путём (нет кодогенератора в базе — он). Остальной JIT на C++ — склейка: обход AST, раздача регистров и меток, вызов кодогенераторов из базы.
- **Компилятор без строк — codegen::eval (2026-10-01, решение автора «всё, с codegen::eval»):**;. Компиляция — вычисление кода программы в контексте цели: цель — сущность (`amd64`, `arm64`; JIT передаёт её значением), её члены — кодирование (`cg.load(…)`, `cg.jump`: вызов функции, объявленной в теле сущности —), операции узлов программы находят свои кодогенераторы в цели сами (`op_codegen(цель, узел, типы)` — оператор узла с типами операндов, вызов по узлу: тип параметра кодогенератора — тег операнда, значение — регистр). Вид узла — тег (`code_kind(e) == n_if`; имена `n_*` — теги видов узлов AST), узел — распаковкой образцом (`array{c, t, e} = code_fields(x)`; пустое поле — ``, проверка `given`). Типы — значения: `jit_type` отдаёт тип, `array(i64)`, `stream(f64)` — функции над типами, `type_of_code(c)` — тип, названный кодом, `type_family(t)` — семейство (`stream`). Регистры модели (`acc`, `second`…) и смещения меток (`target`, `fault`) кодогенераторы берут из окружения компилятора (O4: «из функции получить всё окружение вызова»). Строковые операции (`code_field`, `code_has`, `codegen(строки)`) убраны; операторные символы `=`, `+=`, `&&`, `||` — формы ядра (присваивание, короткая логика). *Моё:* тег — тип с именем структуры узла; вызов по узлу для кодогенераторов; формы ядра по символу. По тестам — 139 функций компилятором на языке, склейкой C++ — ни одной. **Генератор → цикл на языке (2026-10-01):** `spawn { W }` откладывает генератор, `for(x: s)` по его потоку в той же области исполняет W, где `write(s, v)` — тело B с `x = v`; условия свёртки — те же, что у склейки C++ (*моё*): W не пишет наружу и не падает, B не пишет читаемое W и не выходит из цикла, `close(s)` — последнее действие W (перегрузки в W — по типам разбора в контексте встраивания), for — в области spawn. Типы потоков — у разбора всей программы (`jit_type` отдаёт `stream(T)`). Рекурсия встраивания — по цепочке «кто встроил»: блок вызывающего (тело `for`) генерируется в его цепочке, вложенный `for` — не рекурсия. Замер (`bench/fibers.tz 2 20000000`): 1,46 → 0,05 с (без файберов — 0,04). **Память и вывод машинного кода — у VM, через службу (решение автора 2026-10-01):** «контроль памяти нам нужен не столько для управлением временем жизни, а сколько для дампа состояния программы… нормальная програма должна без проблем мигрироваться между vm, между машинами». Шаг 1 — `print`: скаляр — операция службы 6 (биты и тип), строковый литерал — 7 (по узлу), строку печатает `print` VM (вывод совпадает с интерпретатором); выход за границы из машинного кода сообщает индекс и размер (слова значения в области ошибки). Шаг 2 — значения VM: узел, которого компилятор на языке не умеет (`array{…}`, строка, вызов функции ядра — `read_floats`, поле агрегата, `print` нескаляра, вызов с ведущим `require` — выбор перегрузки по значениям), машинный код отдаёт VM (служба, операция 8): номер узла и переменные, которые узел читает (скаляр — биты, нескаляр — номер); VM вычисляет узел интерпретатором, изменённые скаляры возвращает, нескалярный результат кладёт в таблицу значений вызова и отдаёт номер. Таблица — на вызов (адрес — в области аргументов рядом со службой): файберы переключаются внутри машинного кода. Массив в слотах — `{данные, размер, номер}`; данные и размер (операции 9, 10) перечитываются после каждого узла VM. Массив-аргумент — номер ячейки вызывающего. Исправлены свёртки в константу: вызов, меняющий место-аргумент (mut), и узел с рт-проверкой (может бросить — признак наблюдения `throws`) не сворачиваются; чтение ct-переменной модуля — не путь JIT (по месту, §7.3); формы потоков между разборами переносятся по именам типов. **main не житится** (решение автора 2026-10-01): «Есть рядовая лапша - там сплошная динамика… она не житится. Если не рядовая - там где много статики и высокая повторяемость… вот там уже жит работает». *Моё:* узел VM — по месту, с обратной записью скаляров; таблица на вызов.
- **Виды узлов — из ядра в сущности (2026-10-01, решение автора «всё по порядку»):** АСТ — основа, текст — проекция; то, что выражается вызовом или сущностью, не вид узла ядра. Сделано: `require(c)` — вызов ядра (`n_call` с именем `require`, БД `TZDB0018`; ведущие `require` — условие выбора перегрузки, как раньше); `hide x` — вызов ядра `hide` над именем; `try_compile { … }` — вызов ядра с хвостовым блоком; шаблон с тегом — вызов `тег(части)` с записью шаблоном (`n_call.tagged`, `TZDB0021`;); пак повторяющейся клаузы (`catch(A a){…} catch(B b){…}`) — кортеж блоков `array{…}`; `auto` — отсутствие типа, не узел (`TZDB0023`; проекция `auto` не печатает, кроме сигнатуры `&f(auto)`); `a[i]` — парный оператор `[]`; прелюдия объявляет `operator (a)[i] => index(a, i)` (примитив ядра), свои типы перегружают: `operator (grid g)[i64 k] => …`; место `a[i] = v` — форма ядра; массивы и строки — ядро, если перегрузки эти типы не принимают (тест 112). *Моё:* запись объявления `(a)[i]`; компилятор на языке выбирает перегрузку `[]` как перегрузку вызова (`choose`) и встраивает её, `index(a, i)` — примитив ядра; перегрузки `[]` программы не видны в прелюдии — модули — инклюды, прелюдия не включает модуль программы (тест 114). Имена — не только латиница: байты UTF-8 ≥ 0x80 — буквы имени. Точка — операторы:  — `a.x` — постфиксный оператор `.x` (форма ядра, имя — в символе оператора: у узла нет ребёнка-имени), `v.[f]` — оператор `.[]`; `a.f(b)` — вызов, чьё вызываемое — оператор `.f` (≡ `f(a, b)` или член сущности, как раньше). *Моё:* имя в символе `.x`, символ `.[]`. `use` и раскрытие `...t` остаются узлами (решение автора 2026-10-01: цитат «это вызов» нет; `use` — объявление модуля, `...t` — разметка аргумента). `struct Имя { … }` — первое расширение сущности, объявляющее её инстансом `struct` (`n_extend.of`, `TZDB0026`): «у тебя struct будет struct… ты пишешь не struct struct; struct foo{} - где foo - это просто инстанс struct. а далее тебе ничего не мешает сделать foo.bar = ...»; один вид узла — расширение сущности. Итог: из ядра ушли `n_require`, `n_hide`, `n_try_compile`, `n_template`, `n_pack`, `n_auto`, `n_index`, `n_member`, `n_field`, `n_struct` (10 видов).
- **Компилятор на языке:**;. `jit_compile(цель, код функции, типы, результат)` в прелюдии — склейка на tz: обходит AST (`code_field`, `code_has` — поля узла через отражение), раздаёт слоты кадра и метки (два прохода: смещения меток — вторым вызовом кодогенераторов), склеивает байты через `codegen(цель, сущность, типы, аргументы, метка)` — операцию ядра, открывающую кодогенераторы языку (регистровая модель цели — `model` её контекста). JIT сначала зовёт `jit_compile`; пустой массив — не умеет, код даёт склейка на C++ (запасной путь, «существующий компилятор»). Проверка — результаты и qemu AArch64, не побайтовое совпадение со склейкой C++ (своя раскладка: все значения — в слотах кадра, второй операнд — через стек). Подмножество: i64/bool/f64 (тип выражения выводит сам компилятор), операции, цепочки (дерево выбрал разбор экземпляра — JIT передаёт пары «цепочка → дерево», `code_id` сопоставляет узлы), `if`, `loop`/`break`/`continue`, переменные, `return`, `f64(x)`/`i64(x)`; `f64_bits(x)` — биты константы. Массивы-параметры (`xs[i]` с проверкой границ, `xs[i] = v`, `xs.size`), деление и остаток i64 с ловушкой, `require` в теле — тоже. **Вход и ошибки (2026-10-01, решение автора «слот от VM»):** в коде компилятора на языке нет адресов хоста — VM даёт область аргументов (скаляр — слово, массив — {плотные данные, размер}), за ней два слота: вид ошибки и узел; ловушка пишет их и выходит, VM читает после возврата (проверка AArch64 строит ту же раскладку в образе). Регистровая модель цели дополнена третьим рабочим регистром (`rdx`/`x2`). **Вызовы и конструкции (2026-10-01):** семантический инлайн (D10) в компиляторе на языке — перегрузка по типам аргументов (`functions_named` — перегрузки кодом, типы — у разбора), параметр-место — алиас слота, expr-параметр — код вызывающего с его окружением, контекстом встраивания (`inline_context`) и целью `return` (return в блоке — из функции, написавшей блок:), `body(v)` — блок конструкции; `range(n)` — граница, `is_index` — одно сравнение. Типы узлов — у разбора экземпляра (`jit_type(c, ctx)`, `jit_chain`); имя, прочитанное разбором без наблюдения, — по окружению компилятора. `T x = e` — приведение (§5.8). Отказ компилятора — строка-причина в статистике JIT. **Рекурсия (2026-10-01):** вызов себя — настоящий вызов: область аргументов вызываемого собирается в своём кадре (скаляры, массивы — {данные, размер}, слоты ошибки), её адрес — в базу аргументов, `call_self` — относительный call на своё начало (без адресов хоста); ошибка вызванного переносится в свои слоты (вид и узел) и выход. Результат `unit` — тоже. **try/catch/throw (2026-10-01):** `intercept(тело, блоки)` — catch выбран при компиляции по статическому типу брошенного: значение — в переменную catch, переход; ошибка VM в try с подходящим catch (без использования объекта ошибки) — тоже переход; компилятор считает временные на стеке и снимает их при переходе; не пойманное — в слоты области (вид 5, узел, значение, тип: слотов ошибки теперь четыре) и выход. Компилятор возвращает {байты, заметка} — статистика «исключений переходом: N». Константы, известные разбору (`zero(typeof(x))`), — `jit_const(c, ctx)` (значение узла, если оно известно и вычисление чисто — правило склейки C++). Адресный `return(f)`/`return(caller)` (§6.1) — по цепочке «кто встроил» (у каждой встроенной функции — родитель): return(caller) из помощника, вызванного в блоке `for`, выходит из функции, написавшей блок, а не из `for`. **Потоки (2026-10-01):** операция потока — служба VM `jit_vm_service(op, номер, биты, (тип << 32) | узел)`, её адрес VM кладёт в область аргументов (за слотами ошибки) — в коде адресов хоста по-прежнему нет; ответ — {значение, признак ошибки} в двух регистрах C ABI (регистровая модель цели дополнена аргументами C ABI и вторым регистром результата); перед вызовом стек выравнивается, ошибка/отмена в VM — вид 6, VM перебрасывает отложенное исключение. Поток в коде — его номер; тип элементов — из окружения компилятора (разбор называет только `stream`). Проверка AArch64 — заглушка службы в образе. По тестам — 129 функций компилятором на языке, 6 — склейкой C++ (генераторы, значения-функции). `ct` — ключевое слово, имя переменной им быть не может; ошибка разбора прелюдии называет строку. Цена: компилятор интерпретируется — тесты в release 1,4 с (debug −O0 — 23 с). Статистика JIT — «компилятор языка». `code(f)` у имени функции — её объявление. Литерал `0x…` — биты i64 без переполнения (`0x8000000000000000` — знаковый бит). Раскрытие `...a` в `array{…}` — элементы массива (как в аргументах вызова). *Моё:* форма контекста, регистры параметрами, массив байтов как результат.
- Собственные кодогенераторы для **x86-64** и **AArch64** (D8). Без LLVM и без C.
- **Сделано (2026-09-30): AArch64.** Решение автора — цель есть контекст: без абстрактного IR («ллвм-ир… ты не знаешь какие реально у платформы есть регистры/типы», там же). Кодогенерация одна — шаблон по ассемблеру цели (`jit_codegen<A>`); `a64::assembler` даёт те же операции над той же регистровой моделью (аккумулятор, второй операнд, аргументы вызова, переменные в callee-saved), отображённой на AArch64 (`rax`→x9, аргументы → x0–x3, переменные → x19–x23 и d16–d23, временные на стеке — по 16 байт, результат вызова x0→x9, флаги после `fcmp` читаются по-вещественному). ## 11. Граница VM: хост-ОС и C
- `extern "c" { isize write(i32 fd, u8* buf, usize n); }` — импорт функций хоста. Для анализа их эффекты — «не доказано» (§12.1); свойство «вызывает extern» выводится и видно в сущности функции.
- На границе допустимы только представимые типы: примитивы, агрегаты с фиксированной раскладкой (`layout(c)`), указатели.
- Хост-ОС — временная среда. VM абстрагирует хост за своим API, и перенос на железо не меняет семантику программ.
- **Слой хоста** (реализация: `include/tz/os.hpp`) — единственное место, где VM обращается к ОС: файлы отображаются (`mmap`:), stdin/stdout — `read`/`write`. Ввод-вывод программ — сервисы VM поверх этого слоя (§9.5, M3); сейчас (M0/M1) `print`/`read_floats` временно ходят в слой хоста напрямую.
- Модель сервисов не копирует «всё есть файл».

## 12. Безопасность

### 12.1. Различать, а не запрещать (D13)
 «Мутации могут быть как безопасными (т.е. не иметь багов, уб и прочего), либо опасные… БЧ не позволяет использовать мутации вообще… мы в коде хотим оставить и использовать опасное-безопасное, но оградиться от опасного-опасного». Изолированная «ограниченная логика». Поэтому язык **не запрещает** мутации через алиасы, а **классифицирует** их.

**Модель.**
- У каждого алиаса есть **опора** — хранилище, от которого он зависит: элемент вектора опирается на буфер вектора, поле — на агрегат, результат `v.front` — на буфер `v`.
- Операции объявляют, что они делают с хранилищем: `invalidates(self.buffer)` — `push`, `reserve`, `clear` у вектора; `retag(self)` — смена альтернативы `variant` или пост-типа (§5.6); `ends(x)` — `own`-передача и разрушение. Объявления — атрибуты-значения на сущностях библиотеки (§7.4), а не встроенные правила.
- **Опасное-опасное** — операция, инвалидирующая опору, пока живёт алиас, который после этого используется. Сюда же относятся использование после `ends`, алиас, переживший свою опору (сохранён в объект или возвращён дальше её жизни), и одновременная запись в одну ячейку из разных файберов без синхронизации.
- **Опасное-безопасное** — всё остальное. В том числе несколько `mut`-алиасов на один объект, мутация через алиас при живых алиасах на другие поля или элементы, изменение значения элемента без смены буфера. Всё это разрешено.

**Анализ.** Выполняется на инлайн-развёрнутом, специализированном коде в закрытом мире VM. Поэтому он в основном локален. Результат по каждому месту:
| Результат | Что делает VM |
|---|---|
| Доказано безопасно | Ничего |
| Доказано опасно-опасно | Ошибка с трейсом: где создан алиас, где инвалидирована опора, где использован |
| Не доказано | По **уровню статичности** (§12.3): `default` — рантайм-проверка VM (счётчик поколений опоры, проверяется при использовании алиаса; стоит почти ничего и снимается специализатором, где доказано) и предупреждение; `strict` — ошибка |

;.

```tz
v = vec{1, 2, 3};
&e = v[0];     // алиас, опора — буфер v
v[1] = 5;           // опасное-безопасное: буфер не меняется
e = 10;             // ok
v.push(4);          // push: invalidates(v.buffer)
print(e);           // ОШИБКА: e использован после инвалидации опоры (трейс: создан → push → использован)
```

**Сделано (M2c, 2026-09-28).** Ссылки: `auto& e = v[i]` и элемент массива, переданный в изменяемый параметр (`inc(v[2])` — раньше запись терялась на копии), — ссылка на элемент с опорой «буфер `v`»; `auto& a = b` — второе имя ячейки. Ссылка живёт только в переменной и параметре (не хранится в значениях — не переживает опору). Инвалидация: рост (`append`, ядро `push`) и замена массива целиком; библиотека объявляет её атрибутом `[[invalidates(xs)]] push(mut auto xs, auto x)`. Разбор: использование ссылки со старой версией опоры — ошибка с трейсом «взята → инвалидирована → использована»; инвалидация в одной рт-ветке — ошибка тоже (решение: «ошибка в пути»). Исполнение: поколение буфера проверяется при каждом обращении — исключение `invalidated_alias`, память VM не портится. Опасное-безопасное (несколько `mut`-алиасов одного массива, запись в другие элементы) компилируется. *Моё:* ссылки на поля агрегатов и ссылки из ссылок — позже; в машинном коде ссылки — интерпретатор.

**Гарантии** (для кода без `native`/`extern`; эффекты `native`/`extern` — «не доказано», проверяются VM где возможно):
1. Нет обращений к освобождённому или перенесённому хранилищу: они либо доказанно отсутствуют, либо ловятся рантайм-проверкой VM с `throw InvalidatedAlias`, а не повреждением памяти.
2. Нет гонок данных: файберы обмениваются перемещением и каналами; разделяемая изменяемая память — только через типы `sync` (атомики, мьютексы), анализ видит их как синхронизированные ячейки.
3. Границы: индексация проверяется статически, если индекс доказуемо в диапазоне (§5.7), иначе — в рантайме, `throw OutOfBounds`. **Безопасный индекс**: проверка `is_index(k, xs)` в условии (`if(!is_index(k, xs)) break;`) делает значение `k` доказанным индексом `xs` — это **факт на значении**, а не особая форма цикла. Факт привязан к ячейке `xs`, её имени и версии: копия `k` несёт его, новое значение (`k + 1`) — нет; замена `xs` целиком делает его недействительным, рост `xs` — нет. `xs.size` — размер именно этого массива, `range(xs.size)` — его индексы: элемент такого range по доказанному индексу — доказанный индекс `xs` (так `for(auto i: range(a.size)) a[i]` доказывается через библиотечный `for`). Проверка снимается, только если индекс доказан во всех разобранных вычислениях узла. Доказательство делает разбор `check`, отчёт показывает снятые проверки («оптимизация сверху»:); JIT только пользуется этим знанием.
4. Нет UB (§3.5).
5. **Изоляция процессов VM:** процесс не может получить алиас на хранилище другого процесса — между процессами идут только перемещение и каналы (§9.2).

**Нет раздела «безопасный / доверенный код» (`trusted`/`unsafe`).**;. Опасное различается анализом «по месту», а не объявлением. Указатели `T*`, переинтерпретация представлений, `native`/`extern` — обычные средства языка; анализ видит их эффекты как «не доказано» и ставит проверки VM, где может. Рантайм-проверка недоказанной опоры (счётчик поколений) — *моё дополнение*, в духе и.

### 12.2. Память
- **Модель:** VM — ОС, одно адресное пространство (;). Растущий массив или строка — «бесконечный вектор»: свой диапазон адресов, страницы подключаются по мере роста, данные не переезжают (;); метаданные аллокатора — вне данных. Уровень памяти за адресами выбирает программа (`with_alloc`), по умолчанию — контекст вызова. Дамп и состояние программы — страницы как есть, без сериализации и ФС. Шаги: 1 — страницы в VM (**сделано**: плотные массивы и строки — `pages.hpp`; растущий — диапазон 64 ГиБ, мелкий — куски 2^k слов, свободные — списками вне данных; *моё* — размеры и классы); 2 — машинный код держит адрес ячейки значения, данные и размер читает из неё в момент обращения (**сделано**: массив — одно слово, смещения сообщает VM `jit_layout`; узел VM получает переменные адресами, нескалярный результат живёт в памяти контекста вызова и отдаётся адресом; кэша `{данные, размер}` и таблицы номеров нет; `a.f(b) ≡ f(a, b)` в компиляторе на языке; тип элементов `array{}` — по месту использования; тест 116); 3 — struct раскладкой в памяти (**сделано**: поля агрегата — `field_list` в страницах VM, номер поля статичен (`field_index` — порядок полей типа), машинный код читает и пишет поле i64/f64 по смещениям `jit_agg_layout`; bool и нескалярное поле — пока у VM; тест 117); 4 — `with_alloc` (**сделано**: `r = region` — новый уровень (свой диспетчер адресного пространства), `with_alloc(r) { … }` — прелюдия над ядром `alloc_in`: значения, созданные в теле, берут страницы из `r`; без контекста — уровень вызывающего; данные помнят свой уровень — рост и возврат туда же; уровень контекста — у файбера; *моё:* уровень живёт, пока жив процесс; функция с with_alloc — интерпретатору; тест 118); 5 — дамп и энергонезависимое состояние — страницы на тех же адресах (**сделано — состояние программы**, решение автора «состояние программы первым»: `[[state]] x = e` — корень в энергонезависимом уровне; файл держит VM (рядом с программой — `.state`, у программы путей нет; раннер — свой временный каталог, директива `out2:` — второй запуск); страницы отображаются на те же адреса (база — в заголовке), файл плотный (таблица «часть адресов → место в файле»), метаданные аллокатора и корни — в заголовке; запись в ячейку, элемент или поле состояния переносит значение в уровень; в состоянии — только данные (числа, строки, массивы, агрегаты); при открытии — починка уровня памяти и номеров типов и имён полей (у VM они от запуска к запуску свои); элементы общих массивов — тоже в страницах (`value_list`); тест 119. *Моё:* корни по имени, до 256 корней, уровень — 1 ТиБ адресов, растущий вектор в нём — 4 ГиБ; машина процессов `[[state]]` пока не исполняет. Это исключение из решения 2026-09-30 «вне функций — только ct-переменные»: обычные переменные модуля по-прежнему запрещены. **Дамп процесса — страницами (сделано):** всё состояние машины процессов — в своём уровне (полоса адресов процесса, 1 ТиБ, VM выбирает свободную); контейнеры машины берут страницы оттуда (распределитель по классам кусков: размер знает вызывающий, метаданных в данных нет); дамп — заголовок (журнал базы, метаданные уровня, место состояния, имена типов) и страницы как есть, восстановление — те же адреса (;), значения не сериализуются; освобождённый растущий диапазон в полосе остаётся подключённым (без системных вызовов на рост стеков задач). Формат `TZPROC03`. Распределитель — шаблон структуры: правило стиля §6 разрешает их «где иначе нельзя» (контейнеры std). `tz resume` отображает страницы файла дампа на те же адреса копией при записи (файл не меняется). `[[state]]` в машине процессов: значение — из ячейки состояния программы, обратно — при завершении и дампе (как сбрасывает и интерпретатор); тест 119 — интерпретатор, машина, дамп на шагах. Интерпретатор не дампится: его файберы — на стеках хоста, дампируемая форма исполнения — машина процессов (M5).)
- **Кодогенерация — целиком на языке (2026-10-01, путь к раскрутке):** склейка JIT на C++ (`jit_codegen`, ~1 800 строк, и кодировщики инструкций x86-64/AArch64, ~550 строк) убрана — машинный код даёт только компилятор на языке (`jit_compile` прелюдии, цели `amd64`/`arm64` — контексты с кодогенераторами); не смог — интерпретатор с причиной. C++ JIT — разбор экземпляра, исполняемые страницы, вызов, служба VM, проверка AArch64 (`jit/` — 1 100 строк вместо 3 460). Новые уровни памяти — адреса выбирает ядро, закрытые полосы процессов остаются за VM (пул: восстановление дампа в том же процессе — те же адреса); состояние программы открывает только исполняющий программу (`run_main`, машина), не помощники. **Локальные функции в машинном коде:** вызов — встраивание тела в лексическом виде объявления, захваченные имена — места объемлющей функции; операнды — слева направо, как у интерпретатора (у вызовов в операндах бывают эффекты); тест 120. **Рекурсия локальных функций (сделано):** первый вызов — встраивание, рекурсивные — вызов подпрограммы со своим кадром; захват — кадр объемлющей через регистр (`rbx`/`x19`, сохраняется функцией для вызвавшего), номера своих слотов подпрограммы — от отдельной базы (каждое обращение знает свой кадр); аргументы — в регистрах C ABI (до четырёх), подпрограмма генерируется в контексте первого встраивания (там разбор наблюдал тело); ловушка внутри — выход из объемлющей; тесты 121, 122 (AArch64 сходится). **Лямбды-значения (сделано):** аргумент-лямбда связывается с параметром как код определения, лямбда в переменной — как локальная функция; вызов — семантический инлайн с захватом по ссылке, свой выход для return, контекст разбора — места вызова (как `call_value` интерпретатора); тест 123. Вызов замыкания, которое присваивает, не сворачивается в константу (свёртка теряла запись в захваченное, тест 30 с JIT); тип рекурсивного вызова локальной функции — от её внешнего вызова. **Функции в данных — тегами (сделано):** переходы на метки у компилятора — записи `{место, метка, вид, a, b}`, байты по виду даёт `fix_bytes`, вместо замыканий в массиве. **Раскрутка (начата):**. Режим `TZ_JIT_SELF=1`: интерпретатор, исполняющий `jit_compile`, сам использует JIT — функции компилятора компилирует компилятор (повторный вход в компилируемый экземпляр — интерпретатор: запись кэша без кода). Для этого: массив-результат — адрес ячейки значения VM в аккумуляторе (аргумента или памяти вызова; VM берёт значение из неё); имя значения VM в выражении — адрес его ячейки; `...` в `array{…}` — значение VM; пустой массив — поздний тип элементов при слиянии ветвей (`array<?> ⊔ array<T> = array<T>`, *моё*, продолжение позднего типа элементов). Компилируются все кодировщики x86-64 (`x64_rr` … `x64_rex`, `x64_mem`, `x64_rm`); 131 тест проходит и в этом режиме; тест 124. Режим пока медленнее (литералы массивов вычисляет VM через службу) — дальше построение массивов в машинном коде, затем функции компилятора с параметрами-сущностями (`cg`, код, типы).
- Значения живут в переменных (регион функции или файбера). Владеющие контейнеры освобождают память детерминированно при завершении переменной: RAII — следствие того, что объект ведёт себя как.
- Аллокатор задаётся контекстом `with_alloc(a) { … }` (§8.2): арены, пулы, страницы.
- GC — библиотечный аллокатор плюс тип `shared<T>` (разделяемое неизменяемое значение). Он необязателен.

### 12.3. Уровень статичности — выводится, а не задаётся
; «я как раз хочу статичности там, где я могу её получить. Тогда большинство проблем будет решено». Поэтому профилей-запретов нет: у каждой функции (экземпляра) **уровень статичности выводится** и показывается в отчёте `check` — что доказано статически, что проверяется в рантайме (предикаты, границы, опоры алиасов), какие исключения возможны, есть ли выход в интерпретатор/диспатч по `typeid`, вызывает ли `native`/`extern`. Требование «здесь всё должно быть доказано» записывается обычным `require`/`static_assert` над этим выводом (значения компилятора доступны коду, §7).

**Сделано (M2e, 2026-09-28).** В отчёте `check` — раздел «статичность экземпляров»: у каждого экземпляра число рт-проверок (недоказанная граница, рт-делитель, рт-`require`, переполнение в `checked`) с местами и число возможных исключений («покраска»); «всё доказано статически» — если нет ни того, ни другого. Значение `static_level(f)` — агрегат `{checks, throws, detail}` по всем экземплярам `f`, вычисленный разбором всей программы; требование — обычный `ct { require(static_level(sum).checks == 0); }`, невыполненное — ошибка с перечнем недоказанного. *Ограничение:* выход в интерпретатор (JIT) в уровень пока не входит — его показывает `run --jit-stats`.
```tz
ct {
  l = static_level(sum);
  require(l.checks == 0);   // границы доказаны
  require(l.throws == 0);   // исключений нет
}
```

## 13. Среда: как пишется код (слои, пути, срезы)
Это часть ядра, а не «тулинг потом» (D15).. Семантический инлайн без такой среды не работает.

### 13.1. Среда VM
- Редактор, отладчик и инспектор — клиенты VM, работающие с базой и запросами (§10.1).
- VM — **главное состояние**: клиенты шлют операции над узлами, VM применяет их и рассылает изменения всем клиентам.. Транспорт — Unix-сокет на io_uring, бинарный формат (решение автора, 2026-09).
- Главное — АСТ; текст со скобками — лишь одна из проекций. Клиент шлёт **управляющие сигналы** (клавиши, указатель). Курсор — в VM, в координатах АСТ; клавишу толкует активная проекция. VM шлёт узлы и декорации (типы, ошибки, расщепления, статичность);.
- **Протокол v1** (`include/tz/proto.hpp`, `tz serve <программа> <сокет>`): кадр — `u32` длина + сообщение, записанное тем же `writer`, что и журнал (`u32` вид + поля). Клиент → VM: `hello`, `open_view(kind)`, `close_view`, `key(view, key, mods)` — имя клавиши как `KeyboardEvent.key`, `pointer(view, node, piece, offset)`. VM → клиент: `hello`, `view` (узлы: вид и куски проекции — свой текст или место ребёнка), `cursor(view, node, piece, offset)`, `error`. Смещения — в кодовых точках. Куски снимает сам принтер, поэтому синтаксис описан в одном месте. Сценарии `tests/*.wire` гоняют протокол через настоящий сокет и сверяют собранный текст с проекцией. Схема сообщений для клиента — данные (`tz schema`), клиент декодирует их одним обобщённым читателем, без кода под каждый тип. Клиент — `editor/` (Electron): узел — элемент `tz-<вид>`, синтаксис — в Shadow DOM, дети — в light DOM через slots.
- **Ввод:** клавиша правит текст проекции у курсора; переразбирается наименьшая единица вокруг правки — блок, элемент модуля, модуль (сломаны скобки единицы — берутся внешние). Узел единицы сохраняет id; недописанное — дыры, причина дыры — примечание узла, не текст. Проекция сразу каноническая (пробелы ставит она), курсор переносится выравниванием текстов. Правку (`update`: поддерево узла) получают все клиенты.
- **Дополнение:**: путь от места вверх по AST, все блоки одинаковы, конструкции вводят свои имена. Список живой,, ничего не вставляет сам; состояние — в VM. Члены после `.` — типы выражения по всем экземплярам.
- **Добавить по месту (§13.3):**. F12 на вызове — перегрузки, выбранные в экземплярах, все перегрузки и «добавить» для типов аргументов без подходящей; Ctrl+P — то же по сигнатуре. Добавленная — внутренний элемент модуля: в базе и в исполнении, не в представлении модуля; открывается представлением функции.
- **Слои:**. Слой — контекст использования функции (экземпляр: кт — свёрнут целиком, рт — нужен в рантайме); текст один, слой показывает типы, известные значения и не исполняемое в этом контексте.
- **Отладчик — трасса запуска:**. Запуск с записью пути исполнения (узел, значение, глубина, вывод к шагу); шаги вперёд и назад по инструкциям, внутрь и наружу — по встроенным вызовам тоже; VM не останавливается, отдельной «отладочной сборки» нет.
- **Строка набора:** правка инструкции переразбирает только её; набор на пустой строке — новая инструкция на месте; недописанное — дыра только своей строки.
- **Метки проверки:** после каждой правки — реактивный `check`; тип объявленного имени — объединение типов по всем экземплярам (`f64 | i64` у параметра, вызванного с обоими), значок у объявления; ошибка — на узле места, с трейсом инстанцирования (§13.4). Ревизия узла — ревизия его поддерева в пределах функции: правка блока инвалидирует экземпляры функции.
- Редактор — веб на Electron;. DOM — это сам АСТ (Web Components, без virtual DOM).
- Редактирование семантическое. Текстовый ввод сразу разбирается в узлы; дыры видны как дыры.

### 13.2. Пути и срезы
- **Срез по сущности:** «покажи мне только то, что использует эту переменную». VM строит **проекцию**, в которой оставлены только узлы, влияющие на выбранную переменную или выражение или зависящие от него (по потокам данных и управления после инлайна). Проекция — это валидная программа, её можно исполнять и редактировать; правки ложатся в исходные узлы.
- **Программа для входов:**. автор задаёт значения или типы части входов, и специализатор (§10.3) строит **остаточную программу**: развилки свёрнуты, мёртвые ветки убраны, инлайн раскрыт. Её показывают как код в стандартной проекции. Это тот же механизм, что `compile_for`, только отображённый человеку.
- **Путь исполнения:** для записанного выполнения (трейс в VM) — проекция только пройденных узлов, с значениями.

### 13.3. Слои
- **Многослойная функция.**. Функция — узел с **базовым слоем** (логика для статически известного случая) и **слоями**: дополнения для случаев, известных только в рантайме (другие типы, `dyn`-значения, пути ошибок). Слои — это перегрузки и SFINAE-блоки (§5.4), привязанные к одной сущности и показанные редактором как слои одной функции, а не как разбросанные по файлам копии.
- **Согласованность**: общая логика слоёв выносится в базовый слой и **связывается** с ними, а не копируется. Изменение базового слоя реактивно переинстанцирует все слои (§7.3). Открытый вопрос — O12.
- **Добавить по месту:**. Новая перегрузка или специализация создаётся из места использования и привязывается к сущности; поиск и переход идут по сигнатуре, а не по файлам.
- **Расширение конкретной функции ссылкой** на её узел (§5.4).

### 13.4. Диагностика и отладка
- **Диагностика — трейс**: цепочка инстанцирований и специализаций от точки входа до нарушения, с типами и compile-time значениями на каждом шаге. Ошибка перегрузки перечисляет всех кандидатов и ложные или непроверяемые предикаты каждого; исключённые SFINAE-блоки — с причиной. Диагностика объясняет.
- **Отладчик видит инлайн-семантику:** шаги по инлайн-вызовам как по функциям, `return` через функцию показан как выход из вызывающего, `expr`-аргументы — в месте вычисления. Режима «без инлайна для отладки» нет, потому что семантика от инлайна зависит.
- **Инспектор специализаций:** `residual(f)` показывает машинный план, выходы в интерпретатор, диспатчи по `typeid`, рантайм-проверки алиасов и предикатов и причины каждого.
- **Инспектор порядка инстанцирования** (§7.3): какой инстанс что видел, какие ячейки compile-time состояния прочитал и записал.

## 14. Сквозной пример (критерий M0)
```tz
module demo;

dot(a, b) {
  require(a.size == b.size);
  s = zero(typeof(a[0]));
  for(i: range(a.size)) s = s + (a[i] * b[i]);
  s
}

main {
  u = array{1.0, 2.0, 3.0};
  v = array{4.0, 5.0, 6.0};
  print(dot(u, v));              // 1: всё известно → свёрнуто при компиляции до 32.0

  xs = read_floats(stdin);
  ys = read_floats(stdin);
  print(dot(xs, ys));            // 2: require проверяется в рантайме, цикл — JIT

  w = if(args.size > 1) array{1, 2, 3} else array{1.0, 2.0, 3.0};
  print(dot(w, w));              // 3: расщепление — два инстанса dot, без variant

  p = try(parse_int(args[1]));   // 4: семантический инлайн: return из main
}
```
**Критерии M0:**
1. Интерпретатор исполняет пример целиком и выдаёт правильный вывод.
2. `tz check` показывает: (1) `dot(u, v)` свёрнут в кт; (2) `dot(xs, ys)` — экземпляр по рантайм-части `dot(рт array<f64>, рт array<f64>)`; (3) `w` — расщепление на два продолжения без `variant`: при кт-массивах в ветках `dot` свёрнут в каждом продолжении, при рт-данных — по экземпляру на продолжение. После M1 — проверка размера и JIT-цикл.
3. `try` в (4) распознан как `inline_required`; попытка `auto t = try;` — ошибка с трейсом.
4. Правка тела `dot` в работающей VM пересчитывает только `dot` и `main`; следующий вызов идёт в новую версию.

**Статус M0 (2026-09-28, репозиторий `~/tsaryaz`):** выполнено — база AST с бинарным журналом операций (`.tzdb`, импорт текста — операция журнала), двухфазный разбор с локальными дырами, стабильная проекция, интерпретатор по AST, семантический инлайн с адресным `return(f)`/`return(caller)` и `inline_required`, перегрузка через `require`, `try_compile` (только ошибки инстанцирования), режим `check` (value-подход: кт/рт, расщепление продолжений, экземпляры по рантайм-части, рекурсия через неподвижную точку), `tz residual` (программа для входов), `tz slice`. Реактивность: `tz vm` — долгоживущая сессия; правка функции — новый импорт + замена узла в журнале; `check` пересчитывает только экземпляры с изменившимися зависимостями (ревизии узлов), остальные воспроизводит из кэша; `run` сразу идёт в новую версию. Не кэшируются экземпляры с `expr`-аргументами (часть вызывающего), с `mut`/`own`/`out` и с `return(caller)` наружу. Не сделано из M0: операторы кодом (M4), живая замена кода в *работающем* процессе (M3, вместе с файберами).

**Статус M1 (2026-09-28):** свой JIT x86-64. Экземпляр компилируется при первом вызове с типами и кт-значениями из статического разбора; кодогенераторы по узлам AST; плотные массивы i64/f64 передаются машинному коду алиасом; аргумент-место — заём ячейки вызывающего без счётчиков ссылок. **Семантический инлайн в машинном коде (M1b):** нерекурсивный вызов встраивается в контекст — параметры-алиасы слотов вызывающего, `expr`-параметр вычисляется в контексте вызывающего, `return(caller)`/`return(f)` — переход на выход внешней функции; рекурсия и `outline` — настоящий вызов («иная модель функций вместо call/ret» — открытый вопрос). Безопасный индекс снимает проверки границ (§12.1). Изменение параметров выводится (§6.2), пометка `mut` не обязательна; изменяемый скаляр в машинном коде — только при встраивании (при входе из интерпретатора и настоящем вызове он передаётся значением). Деоптимизаций нет: тип массива — его раскладка. **Копия под контекст вызова:** разбор хранит наблюдения по паре (узел, контекст встраивания — цепочка узлов вызова; `expr`-аргумент — в контексте, где написан), JIT берёт типы и кт-значения своего места. **Критерий §14 с JIT:** оба экземпляра `dot` (i64 и f64, расщепление `w`) — машинный код без проверки границ; `zero(typeof(…))` сворачивается разбором. Сессия `tz vm` держит JIT всю жизнь: экземпляр сверяет ревизии вошедших в него функций и после `edit` перекомпилируется, следующий `run` исполняет новый код (тест `32_jit_edit.session`). **Регистры:** переменные с весом (упоминания ×8 за уровень цикла) занимают свободные регистры на время своей области — `rbx`, `r12`–`r15` для целых и буферов массивов, `xmm8`–`xmm15` для f64; раскраски графа нет («распределение регистров — максимально переоценённая херня», но «вечная долбёжка стека» — зло); простой второй операнд — сразу в регистр, без стека; f64-регистры на время настоящего вызова — в домашние слоты. bench: `dot` 100×1M 0.27 → 0.16 с, помощник 200M 0.20 → 0.14 с (C -O2 ≈ втрое быстрее). **M1 закрыт** (2026-09-28). В бэклоге оптимизаций: результат-массив, векторизация.

**Статус M2 (идёт):** **M2a исключения — сделано** (2026-09-28): `try`/`catch`/`throw`-выражения, ошибки VM как исключения своих типов, «покраска» в `check`; в машинном коде `throw` по цепочке встраивания — запись значения и `jmp` в выбранный при компиляции `catch` (критерий «исключение через 3 уровня инлайна = `jmp`», тест `35_jit_exceptions`); ошибка VM внутри `try` — тоже переход; не пойманное в машинном коде — «вторым путём» (как `errno`) в интерпретатор. Ограничения M2a: в машинном коде бросаются скаляры; настоящий вызов внутри `try` — интерпретатор. **Механизм расширений раньше остатка M2** (решение 2026-09-28: «язык сам себя расширяет» — конструкции и проверки M2 делаются на нём): **шаг 1 — сделано**: атрибуты-значения `[[…]]`, расширение `Имя { … }`, `attrs`/`fields`, `quote { … }`/`#x`/`emit`, модульные `ct { }` (§7.4). **Шаг 2 — сделано** (2026-09-28): ядро `loop`/`break`/`continue`, `intercept`, `is_index`; `for`/`while`/`try` — прелюдия на языке; клаузы, блоки с параметрами, хвост-инструкция по объявлению (§4.4); безопасный индекс — факт на значении (§12.1); в машинном коде `break`/`continue` — переход, блок конструкции встраивается с параметрами, `range(n)` — только граница в регистре, `is_index` — одно беззнаковое сравнение (bench `dot` не изменился). Цена: интерпретатор на циклах ≈ 3× медленнее (цикл — вызов библиотечной функции с блоком). **Шаг 3 — сделано** (2026-09-28): все операторы — объявления прелюдии (`operator (a) + (b) => add(a, b)`), приоритетов нет — цепочку разбирает перебор по типам при инстанцировании, `[[associative]]` — инвариант; перегрузки операторов своими типами, постфиксы с `mut`; контекстные условия `[[inside(g)]]` (§4.4). Цена: смешанная арифметика требует скобок (`(x * x) + (y * y)`); bench `dot` не изменился. **M2b typestate — сделано** (2026-09-28): ct-поля («мутируемый constexpr»), `hide`, `own`, расщепление состояния по веткам; исправлено слияние состояния после рт-`if` в разборе (§5.6). **M2c опоры — сделано** (2026-09-28): `auto&`, ссылки на элементы в изменяемых параметрах, `[[invalidates]]`, `push`; ошибка «опасное-опасное» с трейсом, рантайм-поколения (§12.1). **M2d `checked` — сделано** (2026-09-28): контексты `using operator …` для всего выполняемого, экземпляры по контексту (§8.2). **M2e — сделано** (2026-09-28): уровень статичности экземпляров в отчёте и значением `static_level(f)` (§12.3). **M2 закрыт.**

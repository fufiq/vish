## 2. Что есть сейчас

- `include/vish/os.hpp` — единственный слой хоста; программы видят сервисы VM: потоки,
  `open/create` (поток кусков, io_uring), `listen/connect` (поток событий), процессы, права
  `VISH_GRANT`/`proc grant` (spec §9.5). Это уже.
- Но инструменты (`lib/tools.vish`, `versions.vish`, `cli.vish`, `editor.vish`) ходят мимо
  сервисов: `read_text`, `files_in`, `env_*`, `repository_*`, `version_*` — `native "cpp"`,
  внутри — `std::string`/`std::vector`, файлы — C++ (`repository.hpp`, `write_file_atomic`).
- Текст: `find_text`, `slice_text`, `text_from`, `lines_of`, `words_of`, `replace_all`,
  `join_texts`, `in_quotes`, `lower`, `subsequence`, `sorted_*`, `lower_bound` — C++.
  В языке уже есть `s.size`, `s[k]` (и в JIT), `text_byte`, `+`.
- `str_v`/`array_v` — байты/слова в страницах VM (`pages.hpp`): крупные растут на месте
  (свой диапазон адресов — «бесконечный вектор»), мелкие — куски 2^k с копированием (*моё*).
- AST — арена с индексами `node_id`, но узлы держат `std::vector`/`std::string`
  (`ast.hpp`); журнал — `std::vector<journal_entry>`. В C++ VM: `std::vector` ×730,
  `std::string` ×945, `map/unordered_map/set/deque` ×206.
- Репозиторий: формат `VISHREPO04` — C++ сериализует журнал, считает сумму, replay — C++.

## 3. Что изменить (порядок — *моё*)

**Ш1. Сервисы VM вместо примитивов ОС.** Программа не получает пути и fd хоста; VM даёт
ресурсы по правам (отдать/забрать на ходу):
- *хранилище* — именованная область байтов с правами (чтение/запись/рост), отображённая
  в адресное пространство процесса («ренж с правами»); фиксация (`commit`: fsync+rename/lock —
  внутри VM, программа видит одну операцию «зафиксировать»);
- *поток* — уже есть (файлы-куски, сеть-события, stdout/stdin);
- *каталог* — перечень хранилищ, выданных процессу (вместо `files_in`/путей).
C++ остаётся только в `os.hpp` (Linux-реализация сервисов). Позже — тот же интерфейс над
микроядром/железом; программы не меняются.

**Ш2. Текст на языке.** `str` — владеющие байты без срезов; для обхода — диапазон
`(s, from, to)` (как «итераторы в апи»); сборка — буфер+позиция (`text_buffer`: append,
take). Перенести на vish все функции текста из §2; `native` остаётся у `text_byte`,
`text_fixed`. Проверка — существующие тесты + JIT `s[k]`.

**Ш2а. Виды строк** (§4в): растущая (свой диапазон адресов), фиксированная `text<N>`,
буфер+позиция для вывода — типы прелюдии; куски 2^k — реализация по умолчанию.
*Сделано 2026-11-06* (spec §5.9, тесты 370–371): `grown_text`, `fixed_text(N)`, `text_buffer`.

**Ш2б. Сервисы VM на vish** (§4б): хранилище состояния, сеть, ipc, позже криптография —
код уровня VM в общей базе, одна копия, вызов в контексте вызывающего, доступ по правам.

**Ш3. Отражение базы.** Узлы и журнал — значения языка: `node_kind`, поля по типам
(не по именам строк — `codegen::eval`), дети, создание узла вида с полями, записи журнала
по номеру. Основания:,.
*Сделано 2026-11-06* (spec §7.4 «База как значения», тесты 372–373): `code_at`, `code_kinds`, `k{…}` по значению-типу, `journal_size/journal_entry`.

**Ш4. Репозиторий на языке** (по решению пользователя заменяется Ш5; формат/проверка — на vish над ареной). Формат, сумма, проверка, replay — `lib/versions.vish`
поверх Ш1 (хранилище) и Ш3 (журнал). C++: только сервис хранилища.

**Ш5 (отдельно, большой рефакторинг). Арена AST в хранилище.** Узлы без `std::vector`/
`std::string`: дети и строки — индексы в аренах (относительная адресация); арена базы — в
хранилище Ш1, т.е.. Тогда сохранение = фиксация хранилища,
сериализатор журнала не нужен. Вместе — замена контейнеров std в ядре по §6 стиля
(арены+индексы) там, где это память программы, а не временные структуры C++.

## 4. Развилки для пользователя

1. «Абстракции, а не примитивы» vs автор («ОС — полноценный интерфейс к железу…
   в юзерпейсе строишь что хочешь»). Предлагаю: VM даёт *ресурсы с правами* (хранилище,
   поток, процесс), а форматы/протоколы/репозиторий — язык. Подтвердить.
2. «Потом сразу к железу» vs и
: на железо идёт *VM как ОС*
   (микроядро: память/процессы), программы — никогда напрямую; «вм где будет запускаться…?» —
. Подтвердить.
3. Ш4 без Ш5 (сериализация на vish) или сразу Ш5 (арена в хранилище).
4. Мелкие строки: оставить куски 2^k (*моё*) или каждой строке — растущий диапазон
 ценой адресов/страниц.

## 4а. Решения пользователя (2026-10-29)
- Путь к железу: **VM как ОС** — сейчас поверх Linux (`os.hpp`), потом VM на железе
  (микроядро: память/процессы, Linux — гость для драйверов); программы — всегда под VM,
  интерфейс сервисов не меняется.
- Хранение: **сразу арена в ммапе** (Ш5 вместо Ш4): узлы без `std::vector`/`std::string`,
  сохранение = фиксация памяти; сериализатор журнала не нужен.
- Граница VM/языка: **принято** предложение §4б (библиотеки — общая база AST, сервисы — vish
  уровня VM, C++ — только `os.hpp`).
- Строки: **принято** предложение §4в (виды строк — типы, выбирает код) — шаг Ш2а.

Предложение (*моё* по этим цитатам):
- **Библиотеки** — не `.so` и не линковка: код в общей базе AST VM, одна копия, типы закрыты
  на всю VM; программа ссылается на сущности базы.
- **Сервисы VM** (хранилище состояния, сеть, ipc, криптография, позже окно/звук) — код на
  vish уровня VM, общий для всех процессов, исполняется в контексте вызывающего (spec §9.5);
  программе — только по правам. C++ — лишь `os.hpp` (Linux сейчас, железо потом).
- **Хранилище состояния** = сервис: арена программы в
  ммапе (решение автора), VM может её фиксировать, переносить, просить освободить.
- Отсюда граница: снизу C++ даёт VM полный низкий интерфейс, *программам* VM
  даёт абстракции-сервисы, написанные на vish.

## 4в. Мелкие строки 
- На «для строки в 96 символов у вас 4000 байт уйдёт в никуда»: «Зачем мне для мелких строк
  использовать строки?… другую строку. Ту, которая будет эффективнее и удобнее в данном случае»;
  «я выступаю за подход - каждой задаче своя строка»; «после malloc(50gb) памяти занятой ровно
  ноль… в процессе использования память растёт. Сама».
- SSO — «самый очевидный случай» буфера фиксированного размера.
- Предложение (*моё*): виды строк — типы, выбирает код: растущая (свой диапазон адресов),
  фиксированная `text<N>` (буфер в значении), буфер+позиция для вывода; текущее «мелкие —
  куски 2^k» остаётся реализацией по умолчанию до появления видов.
